Os 9 fundamentos — e por que cada um importa

1

Fundamentos de LLMs

O modelo continua texto: instruções definem comportamento, contexto é a única memória, tokens limitam a janela, ferramentas dão capacidade de agir.

  • Por que importa: sem saber isso, culpa-se o modelo pelo que é pedido ruim ou contexto mal montado.
  • Evidência: src/app/api/chat/route.ts (persona, histórico limitado, provider por env).
2

Harness

O programa que organiza modelo + contexto + execução (Claude Code, Codex, OpenCode, Qwen Code). O modelo é o motor; o harness é o carro.

  • Por que importa: é o harness que decide o que entra no contexto e quando agir — qualidade nasce dessa orquestração.
3

Prompt Engineering

Papel + regras + formato. A fórmula: Contexto + Tarefa + Formato.

  • Por que importa: ambiguidade no pedido vira retrabalho na entrega. Spec com requisitos numerados é prompt engineering aplicado a código.
4

Context Engineering

Selecionar arquivos, regras e memórias relevantes — e excluir o ruído.

  • Por que importa: contexto cheio de código irrelevante degrada a resposta tanto quanto prompt ruim.
  • Evidência: .agents/notes/, worklog.md, QWEN.md.
5

PRD e Specs

PRD define o problema; spec transforma problema em contrato executável. Regra de ouro: cada critério de aceite vira teste.

  • Por que importa: é o que dá previsibilidade — o caso 0 entregou exatamente R1–R6, sem surpresa.
6

Execução guiada

Plan mode (investigar sem tocar) → Build mode (passos com gates). Falhou? Diagnostica, não retry no escuro.

  • Por que importa: gates são a diferença entre "acho que funciona" e "está provado que funciona".
7

Agentes e subagentes

Delegar com missão, fronteiras e definição de pronto. Protegem o contexto principal e permitem paralelismo.

  • Por que importa: delegação sem brief é perda de controle; com brief + verificação, é multiplicador (W6).
8

MCP, ACP e Skills

MCP conecta ferramentas/dados; ACP padroniza cliente↔agente; Skills empacotam comportamento reutilizável.

  • Por que importa: transformam padrão de qualidade de "conhecimento tribal" em ativo invocável por nome.
9

Loop Engineering

Medir → agir → verificar → registrar, com condição de parada e teto de iterações.

  • Por que importa: sem parada é desperdício; sem verificação independente é autoengano (W7).

Como está funcionando — diagramas

Fontes em docs/workflow-dev-ia/diagrams/*.mmd (re-renderizável com mermaid).

1 · Arquitetura do sistema (runtime)

SPA de página única → store Zustand → 18 rotas API finas → duas seams profundas (leitura: snapshot() · escrita: pipeline transacional) → Prisma/SQLite. O LLM vive isolado no /api/chat com provider trocável por env. Os gates verificam todas as camadas.

2 · O coração do jogo — pipeline de conclusão de lição

Toda tentativa passa pelo grader e vira uma única transação (XP/gemas/corações, streak, liga, conquistas, log) dirigida por um clock injetado — o snapshot() reflete o resultado na UI. É o "módulo profundo" do repo: interface simples, complexidade escondida.

3 · O que foi entregue — linha do tempo

Da fundação (esquema, currículo, UI, arte) ao loop de QA (conquistas, playground, prática, shop), passando pelo aprofundamento de arquitetura (seams + suítes de teste + E2E + LLM in-app) até o sistema de qualidade desta semana (spec-first, bugs provados, kit de workflows e skills).

Padrões transversais — o que se repetiu nos 11

1 · Claim → Proof

Nada entrou no repo por autoridade. Teste red antes do fix (W1), testes antes do módulo (W2), suíte antes/depois (W3), leitura do diff (W4), 1 teste para 29 falhas (W5), inspeção das alegações (W6), re-medição (W7), rodar o ativo criado (W10).

2 · Falha é dado

As duas grandes falhas do dia (lockfiles, 29/29 E2E) foram resolvidas por diagnóstico de causa raiz. Retry cego teria custado tempo e escondido a causa.

3 · Uma coisa por fluxo

Cada workflow entregou UMA coisa; o resto virou próximo passo registrado. O "aproveitar e..." é como qualidade morre.

4 · Tudo vira ativo

Testes, notas, templates, scripts, specs preenchidas. Qualidade não codificada se paga de novo a cada sessão; codificada, compõe.

5 · Ambiente é padrão

Lockfile, config do Playwright, build do browser, path do banco — nada disso é "só ambiente". Foi onde o dia mais ensinou.

O principal — se for pra levar UMA coisa

Verificação independente de tudo que a IA produz.

A IA acelera a geração — código, spec, review, auditoria saem em minutos. Isso muda a economia, mas não muda o que "pronto" significa. O dev que usa IA com qualidade desloca o trabalho de escrever para especificar + verificar:

  • contrato antes de código (a spec é o pedido);
  • gate automatizado depois de cada passo (não depender de memória);
  • inspeção por amostra do que foi delegado (auditar a auditoria);
  • registrar o resultado real (saída de comando), não a intenção.

A saída da IA é sempre uma hipótese; o workflow é o que a transforma em fato.

Modelos mudam, harnesses mudam, skills mudam — a disciplina de verificar é a única parte portátil do padrão de qualidade.
