Parte 01

Fundamentos de LLMs para quem escreve código

Antes de dominar Claude Code, Codex ou OpenCode, você precisa entender a máquina por baixo: um modelo que prevê o próximo token, não guarda estado e enxerga o mundo através de uma janela de contexto finita.

Previsão do próximo token: é isso, o resto é consequência

Um LLM (Large Language Model) faz uma única coisa: dado um texto de entrada, ele calcula uma distribuição de probabilidade sobre qual será o próximo token — e repete isso token a token até terminar. Esse processo é chamado de autoregressivo: cada token gerado é anexado à entrada e vira parte do contexto para prever o seguinte. Não existe um "plano" armazenado em algum lugar; a coerência de uma resposta longa emerge dessa repetição, com o texto já produzido servindo de guia para o que vem depois.

Para você, dev, a consequência prática é direta: tudo que influencia a saída do modelo precisa estar no texto de entrada. Se uma convenção do seu projeto, um trecho de código ou uma restrição de negócio não está no contexto, para o modelo ela não existe. Não há "memória do projeto" mágica — há o que foi enviado neste turno.

Tokens e tokenização

O modelo não lê caracteres nem palavras: lê tokens, fragmentos de texto definidos por um tokenizador treinado por frequência estatística. Palavras comuns em inglês costumam virar 1 token; palavras em português, identificadores compostos e sintaxe de código são quebrados em mais pedaços. Isso importa porque token é a unidade de tudo — custo, limite de contexto e velocidade são medidos em tokens.

Janela de contexto: o que realmente entra nela

A janela de contexto é o total de tokens que o modelo consegue processar em uma única inferência: entrada + saída. Quando você conversa com um agente de código, a janela não contém só a sua última mensagem. Ela carrega:

  • System prompt — as instruções do harness (Claude Code, Codex etc.), definições de ferramentas, regras do seu CLAUDE.md ou AGENTS.md;
  • Histórico completo da conversa — todas as suas mensagens e todas as respostas do assistente até aqui;
  • Arquivos lidos — cada arquivo que o agente abriu vira texto dentro do contexto;
  • Saídas de ferramentas — o resultado de cada comando de shell, cada diff, cada log de teste.

E aqui está o ponto que mais confunde iniciantes: o modelo é stateless. Ele não "lembra" do turno anterior. A cada nova mensagem sua, o harness reenvia a conversa inteira — system prompt, histórico, arquivos, resultados de ferramentas — e o modelo processa tudo do zero. A sensação de continuidade é uma construção do cliente, não uma propriedade do modelo. Por isso conversas longas ficam mais caras e mais lentas a cada turno: o custo é proporcional ao contexto acumulado. Esse fato é a raiz de quase tudo em engenharia de contexto.

Papéis: system, user, assistant

APIs de chat estruturam o contexto como um array de mensagens com papéis. O system define comportamento e restrições; user são as suas mensagens; assistant são as respostas anteriores do modelo (reenviadas, porque stateless). Um turno real de uma sessão de desenvolvimento se parece com isto:

Como as instruções são processadas

Internamente, o mecanismo de atenção permite que cada token gerado "olhe" para todos os tokens do contexto e pese a relevância de cada um. Não há execução sequencial de regras: o system prompt, o histórico e o arquivo lido competem por influência ao mesmo tempo. Na prática, três regras emergem desse mecanismo:

  1. System prompt tem precedência

    Modelos são treinados para dar peso maior às instruções de sistema. É por isso que o harness coloca ali as regras invioláveis — e por isso seu CLAUDE.md funciona: o harness o injeta no contexto de toda sessão com tratamento de instrução prioritária de projeto.

  2. Especificidade vence vagueza

    "Corrija o bug de validação em createOrder retornando 422 com corpo { error: 'empty_cart' }" produz resultado muito mais previsível que "conserta o endpoint de pedidos". Instrução vaga deixa o modelo preencher lacunas com o padrão estatístico do treinamento — que pode não ser o padrão do seu projeto.

  3. Tudo no contexto influencia — inclusive lixo

    Um log de erro antigo, um arquivo irrelevante lido "por via das dúvidas" ou uma instrução contraditória de dez turnos atrás continuam recebendo atenção. Contexto ruim degrada saída boa.

Tool use: como o modelo "executa" coisas (spoiler: ele não executa)

Modelos não rodam comandos, não acessam disco, não fazem requisições. O que existe é tool use (function calling): o harness descreve ferramentas disponíveis no contexto e, quando o modelo decide usar uma, ele emite texto estruturado — uma chamada com nome e argumentos. Amostragem e temperatura

A saída do modelo em cada passo é uma distribuição de probabilidade sobre todos os tokens possíveis; a amostragem escolhe um deles. A temperatura controla o quanto essa escolha se afasta do token mais provável: valores baixos (perto de 0) tornam a saída quase determinística e conservadora — bom para código, extração de dados e correções; valores altos aumentam a diversidade e o risco — às vezes útil para brainstorming, quase nunca para diffs. Ferramentas de código geralmente já usam temperatura baixa por padrão, e mesmo em temperatura 0 pode haver pequenas variações entre execuções. Não trate temperatura como botão mágico de qualidade: prompt e contexto pesam muito mais.

Limitações práticas que você vai encontrar hoje

Alucinação

O modelo gera o token mais plausível, não o mais verdadeiro. Ele inventa APIs que não existem, flags de CLI plausíveis-mas-falsas e imports de pacotes inexistentes com total confiança. Antídoto: dar a documentação real no contexto e verificar com execução (testes, compilador), nunca com leitura.

Degradação com contexto longo

Janelas grandes não significam atenção uniforme. Em contextos muito cheios, informação no meio tende a ser ignorada (lost in the middle) e a qualidade cai gradualmente (context rot). Sessões intermináveis com dezenas de arquivos lidos ficam piores, não melhores.

Custo por token

Você paga por token de entrada e de saída — e a entrada é reenviada inteira a cada turno. Uma conversa de 50 turnos com arquivos grandes no histórico multiplica custo e latência. Contexto enxuto é otimização de dinheiro, não só de qualidade.

Nunca confie em fato gerado sem verificação. Se o modelo afirma que uma função existe, que um teste passa ou que uma flag é válida, isso é uma previsão estatística até você executar e ver. Agentes de código bons fecham esse ciclo sozinhos — rodando o teste — mas a responsabilidade final pela verificação é sua.
Modelo mental para levar adiante. Pense no LLM como uma função pura e cara: f(contexto) → próximos tokens. Toda técnica das próximas seções — prompt engineering, context engineering, loop engineering — é, no fundo, engenharia do argumento dessa função.

Glossário da seção

token
Menor unidade de texto que o modelo processa; fragmento de palavra definido pelo tokenizador. Unidade de medida de custo, contexto e velocidade.
autoregressivo
Modo de geração em que cada token produzido é anexado à entrada e usado para prever o token seguinte, um por vez.
janela de contexto
Limite total de tokens (entrada + saída) que o modelo processa em uma inferência; contém system prompt, histórico, arquivos e resultados de ferramentas.
system prompt
Mensagem com papel de sistema que define comportamento, regras e ferramentas; recebe precedência sobre as demais instruções.
inferência
Execução do modelo sobre um contexto para gerar saída. Cada turno de conversa é uma inferência nova e independente — o modelo é stateless.
temperatura
Parâmetro de amostragem que controla a aleatoriedade da escolha do próximo token; baixa para código e tarefas determinísticas, alta para diversidade.
tool use
Mecanismo em que o modelo emite uma chamada estruturada (nome + argumentos) e o harness executa a ação real, devolvendo o resultado ao contexto.
alucinação
Saída plausível porém falsa — APIs, arquivos ou fatos inventados — consequência direta de o modelo otimizar plausibilidade, não verdade.
Parte 02

Harness: o software ao redor do modelo

O modelo sozinho só transforma texto em texto. Quem monta o loop agêntico — ferramentas, contexto, permissões e a decisão de continuar ou parar — é o harness.

O que é um harness

Quando você digita "corrige o teste que está quebrando" no Claude Code, o modelo não recebe só essa frase. Ele recebe um system prompt do produto (instruções longas sobre como se comportar como agente de código), a definição das ferramentas disponíveis (ler arquivo, editar arquivo, rodar comando, buscar no repositório), o contexto coletado (memória de projeto, estado do git, trechos de arquivos já lidos) e o histórico da conversa. O software que monta esse pacote, envia para o modelo, executa o que o modelo pedir e repete até a tarefa terminar é o harness — literalmente, o "arnês" que acopla o modelo ao seu ambiente de desenvolvimento.

Isso importa porque, como você viu em Fundamentos de LLM, o modelo é uma função sem estado: cada chamada recebe tudo do zero. O harness é quem mantém o estado entre chamadas, decide o que entra na janela de contexto, aplica os portões de segurança e transforma "pedidos de ferramenta" em ações reais no seu filesystem. O modelo propõe; o harness dispõe.

O loop agêntico

No coração de todo harness existe o mesmo loop. O modelo responde; se a resposta contém um pedido de ferramenta, o harness executa (depois de checar permissões) e devolve o resultado como nova mensagem; se não contém, a tarefa terminou e o texto final vai para você. Em pseudocódigo:

Um grep que retorna 40 mil linhas cruas afoga o contexto; um harness bom trunca, pagina e sinaliza o corte. A qualidade da engenharia ao redor muda o resultado tanto quanto o modelo.

você → harness → contexto + prompt → modelo → tool call → harness executa → repete até terminar → resposta

Anatomia de um harness de código

Todo harness sério de desenvolvimento assistido tem, com nomes diferentes, as mesmas oito peças:

System prompt do produto

Instruções fixas que definem o comportamento do agente: como usar ferramentas, quando pedir confirmação, estilo de código, convenções de commit. Você não escreve esse prompt — o fabricante escreve — mas ele explica por que o mesmo modelo se comporta diferente em produtos diferentes.

Definição de ferramentas

Um catálogo de funções com nome, descrição e schema de parâmetros: ler arquivo, editar por substituição exata, rodar comando no shell, buscar por regex, buscar na web. O modelo escolhe entre elas; o harness executa e devolve o resultado.

Gestão de contexto (compaction)

A janela de contexto é finita. Quando a conversa cresce demais, o harness compacta: resume turnos antigos, descarta saídas de ferramenta obsoletas, preserva o que importa. Feito mal, o agente "esquece" decisões do início da sessão — tema da Parte 04.

Permissões e sandbox

Portões entre a intenção do modelo e o efeito real: aprovar cada edição, permitir comandos por padrão de allowlist, rodar tudo dentro de um sandbox sem rede. É o que separa "agente útil" de "processo com acesso irrestrito ao seu shell".

Memória de projeto

Arquivos como CLAUDE.md ou AGENTS.md na raiz do repositório, injetados automaticamente em toda sessão: convenções, comandos de build e teste, armadilhas conhecidas. É a peça que você mais controla no dia a dia.

Slash commands

Prompts parametrizados salvos como arquivos (ex.: /revisar-pr, /gerar-migration). Transformam um fluxo que você repetiria à mão em um comando de uma linha, versionado junto com o código.

Hooks

Scripts seus que o harness dispara em eventos do loop: antes de executar uma ferramenta, depois de uma edição, ao fim da sessão. Servem para rodar lint automático após cada edição ou bloquear comandos que toquem em produção — garantia determinística, não promessa do modelo.

Subagentes

O agente principal delega uma subtarefa (ex.: "mapeie onde esse endpoint é consumido") a uma instância separada, com contexto próprio. O subagente queima milhares de tokens explorando e devolve só o resumo — o contexto do agente principal fica limpo.

Três harnesses, mesma ideia

Claude Code, Codex e OpenCode implementam o mesmo loop com escolhas diferentes de produto. Conhecer as diferenças ajuda a transferir o que você aprende de um para o outro — e a escolher a ferramenta certa por contexto (empresa que já paga OpenAI, necessidade de rodar modelo local, etc.):

O harness importa tanto quanto o modelo. O mesmo modelo, com o mesmo pedido, rende resultados diferentes conforme o contexto que o harness montou, as ferramentas que expôs e os portões que aplicou. Quando um agente "fica burro", a causa costuma estar no lado do harness — contexto poluído, ferramenta devolvendo lixo, memória de projeto desatualizada — antes de estar no modelo. É por isso que as próximas seções tratam de engenharia de prompt e de contexto: são as alavancas do harness que estão nas suas mãos.
Portões existem por um motivo. É tentador aprovar tudo automaticamente para "ir mais rápido". Antes de afrouxar permissões, entenda o que cada portão protege: edição sem revisão pode sobrescrever trabalho não commitado; comando sem allowlist pode apagar dados ou vazar segredos via rede. O caminho maduro é afrouxar seletivamente — allowlist para comandos de leitura e testes, aprovação manual para o resto — como você verá em Execução guiada.

Onde você entra

Do lado do fabricante ficam o system prompt do produto, o executor de ferramentas e a compaction. Do seu lado ficam a memória de projeto, os slash commands, os hooks, a configuração de permissões e os servidores MCP que você conecta. Dominar desenvolvimento assistido é, em grande parte, aprender a operar essas alavancas — e é exatamente o roteiro das partes seguintes.

Parte 03

Prompt Engineering

Um bom prompt não é mágica: é uma especificação curta e verificável. Aqui estão os sete princípios que separam "pediu algo e torceu" de "descreveu o problema e recebeu a solução certa".

Por que isso importa mais em código do que em texto

Quando você pede um parágrafo de marketing e ele sai 20% pior do que o esperado, você edita e segue. Quando você pede uma correção de bug e o prompt é ambíguo, o modelo escolhe uma interpretação plausível — e plausível não é o mesmo que correta. O agente vai executar essa interpretação: editar arquivos, rodar testes, talvez abrir um PR. O custo de um prompt vago em desenvolvimento assistido não é um texto mediano; é retrabalho, diffs enormes para revisar e, no pior caso, uma "correção" que mascara o bug em vez de eliminá-lo.

A boa notícia: prompts eficazes para código seguem uma estrutura previsível. Você não precisa de criatividade, precisa de disciplina.

1. Estrutura: contexto → tarefa → restrições → formato

Essa ordem funciona porque espelha como o modelo processa a requisição: primeiro entende o cenário, depois o objetivo, depois os limites, e por fim o que entregar. Veja um prompt completo para um bug realista — um endpoint de paginação que retorna itens duplicados entre páginas:

2. Especificidade e critérios de aceite verificáveis

"Corrija o bug" não tem critério de sucesso. "Adicione um teste que reproduza a duplicação antes do fix e passe depois" tem. Critérios de aceite dentro do prompt funcionam como um contrato executável: o agente sabe quando parou de trabalhar e você sabe o que verificar. Bons critérios são binários (passa ou não passa) e checáveis por comando:

  • Verificável: "o teste orders.pagination.test.ts passa", "nenhum item aparece em duas páginas consecutivas num dataset de 1000 registros com timestamps iguais", "npm run lint sem novos avisos".
  • Não verificável: "a paginação deve funcionar bem", "o código deve ficar limpo", "melhore a performance".

3. Diga o que fazer, não só o que evitar

Modelos seguem instruções positivas melhor do que negativas. "Não use any" deixa em aberto o que usar; "tipe o retorno com a interface Order de src/types/order.ts" fecha a questão. Restrições negativas ainda têm lugar — "não mude o contrato da API" no exemplo acima é uma —, mas cada "não faça X" idealmente vem acompanhado do "faça Y no lugar". Compare: "não quebre os testes existentes" vs. "rode npm test antes de finalizar e corrija qualquer regressão que a sua mudança introduzir". A segunda versão diz o que fazer quando a restrição for violada.

4. Exemplos (few-shot) quando o formato importa

Descrever um formato em prosa é impreciso; mostrar dois ou três exemplos é exato. Isso vale para mensagens de commit, formato de changelog, estrutura de resposta de API, convenções de nomenclatura de testes. Um caso clássico — padronizar mensagens de commit do agente:

Regra prática: se você consegue descrever o formato em uma frase inequívoca, descreva; se a descrição começa a acumular exceções, mostre exemplos.

5. Declare o formato da resposta esperada

Sem instrução de formato, o modelo escolhe por você — geralmente prosa longa com blocos de código intercalados. Se você vai colar a saída num script, peça JSON com o schema explícito. Se vai revisar, peça "diff primeiro, justificativa depois". Se é diagnóstico, peça "causa raiz em 3 frases antes de qualquer código". O bloco ## Formato da resposta do exemplo de paginação faz exatamente isso: quatro itens numerados, e a resposta chega pronta para o seu fluxo de revisão em vez de exigir garimpo.

6. Em tarefas grandes, peça o plano antes do código

Para um fix pontual, plano é burocracia. Para "migrar a autenticação de sessão para JWT" ou "extrair o módulo de billing para um pacote separado", pedir código direto é receita para um diff de 40 arquivos que você não consegue revisar. A instrução é simples: "Antes de editar qualquer arquivo, apresente um plano com as etapas, os arquivos afetados em cada uma e os riscos. Aguarde minha aprovação." Isso cria um ponto de inspeção barato: corrigir um plano custa uma frase; corrigir uma implementação enviesada custa uma tarde. Ferramentas como o Claude Code têm modos de planejamento nativos para isso — o tema aprofunda em Execução guiada e PRDs e specs.

7. Itere: prompt é rascunho, não contrato

O primeiro prompt raramente é o definitivo, e tudo bem. O fluxo saudável é: envie, leia a resposta, identifique onde o modelo divergiu da sua intenção, e corrija a instrução — não apenas o resultado. Se o agente refatorou além do escopo, a próxima mensagem não é "desfaça"; é "desfaça e daqui em diante altere somente listOrders()". Quando a mesma correção aparece três vezes em sessões diferentes, ela deixou de ser ajuste de prompt e virou regra de projeto: mova para o CLAUDE.md ou equivalente (ver Context Engineering). Prompts descartáveis se refinam na conversa; instruções recorrentes se promovem a configuração.

A mesma tarefa, duas versões

❌ Vago

O modelo não sabe onde olhar, o que pode mudar, nem quando terminou. Resultado típico: ele reescreve a paginação inteira para cursor (mudando o contrato da API), não adiciona teste, e entrega um diff grande que você precisa auditar linha a linha para descobrir se o bug original sequer foi entendido.

✅ Preciso

Mesma tarefa, dez linhas. Contexto, hipótese, escopo, critério de aceite e formato. O diff resultante tende a ser pequeno, focado e verificável com um comando.

Não existe prompt mágico. Nenhuma formulação compensa o modelo não ter acesso ao arquivo certo, ao erro real ou à convenção do seu projeto. Se as respostas vêm genéricas ou erradas apesar de um prompt bem estruturado, o problema quase sempre é o que está (ou não está) na janela de contexto — e isso se resolve em Context Engineering, não trocando "corrija" por "corrija cuidadosamente".

Checklist antes de enviar

  • O prompt diz onde está o problema (arquivo, função, endpoint) ou dá pistas suficientes para localizar?
  • Existe pelo menos um critério de aceite binário e verificável por comando ou teste?
  • O escopo está delimitado — o que pode mudar e, principalmente, o que não pode?
  • As restrições estão formuladas como "faça Y", não apenas "evite X"?
  • Se o formato da saída importa, ele está declarado ou demonstrado com exemplos?
  • Se a tarefa toca mais de um punhado de arquivos, você pediu plano antes de código?
  • Você incluiu sua hipótese como hipótese ("suspeito que..."), sem travar a investigação?
  • Essa instrução já se repetiu em outras sessões? Se sim, promova-a ao CLAUDE.md em vez de redigitar.
Parte 04

Context Engineering

A janela de contexto é finita e o desempenho do modelo degrada com informação irrelevante. Engenharia de contexto é a disciplina de decidir o que entra, quando entra e em que forma.

O problema: a janela não é infinita — e nem deveria ser tratada assim

Todo modelo trabalha dentro de uma janela de contexto: o total de tokens que ele consegue "enxergar" de uma vez, somando instruções, arquivos, histórico da conversa e a própria resposta em construção. Janelas modernas são grandes (centenas de milhares de tokens, dependendo do modelo), mas dois fatos permanecem verdadeiros independentemente do tamanho: primeiro, a janela acaba; segundo — e mais importante — o desempenho degrada antes de ela acabar. Um modelo com a janela cheia de código irrelevante comete mais erros do que o mesmo modelo com um décimo do conteúdo, todo relevante.

Isso muda o jogo. A pergunta deixa de ser "quanto contexto cabe?" e vira "qual é o menor conjunto de informação que torna esta tarefa resolvível?". Se prompt engineering é escrever bem a instrução, engenharia de contexto é curar tudo que cerca a instrução. Na prática de desenvolvimento assistido por IA, é a habilidade que mais separa quem obtém resultados consistentes de quem fica frustrado com o harness.

Tokens são orçamento. Cada token irrelevante na janela compete com os relevantes pela atenção do modelo. Não é só custo financeiro: é custo de precisão. Antes de colar qualquer coisa no contexto, pergunte: "isso ajuda a resolver esta tarefa, ou só ocupa espaço?"

De onde vem o contexto

Numa sessão de trabalho com Claude Code, Codex ou OpenCode, o contexto do modelo é montado a partir de fontes distintas, cada uma com um regime próprio de seleção:

Arquivos do repositório

A maior fonte — e a mais perigosa. A regra é busca dirigida: grep para localizar, leitura de trechos para confirmar. Nunca despeje uma pasta inteira na janela.

Regras persistentes

Arquivos como CLAUDE.md e AGENTS.md, carregados em toda sessão. Comandos do projeto, convenções, restrições. Custam tokens sempre — mantenha enxutos.

Memórias

Decisões de arquitetura e lições de sessões passadas ("migramos para Vitest em março", "o cliente HTTP tem retry embutido, não duplique"). Evitam que o agente re-descubra — ou re-erre — o que já foi resolvido.

Documentação externa

Docs de bibliotecas e APIs, na versão que o projeto usa. O conhecimento de treino do modelo pode estar defasado; docs da versão errada são piores que nenhuma.

Diffs

O diff da mudança em andamento é contexto de altíssima densidade: mostra exatamente o que mudou, sem o ruído do arquivo inteiro. Ideal para revisão e para retomar trabalho.

Erros de teste e stack traces

Provavelmente o token mais valioso que existe. Uma falha de teste com stack trace aponta arquivo, linha e comportamento esperado vs. obtido. Cole o erro, não a sua paráfrase dele.

Seleção dirigida: grep primeiro, leitura depois

O anti-padrão mais comum é o despejo: "aqui está a pasta src/ inteira, encontre o bug". Isso enterra as três linhas que importam sob milhares que não importam. O padrão correto é um funil: busque por termos específicos (nome da função, mensagem de erro, rota da API), leia apenas os trechos que a busca apontou, e só então expanda se necessário. Ferramentas agênticas fazem isso sozinhas quando bem instruídas — mas você acelera tudo quando já aponta a direção: "o bug está no fluxo de checkout; comece por services/payment.ts e pelo teste que falha".

❌ Despejar 15 arquivos e torcer

"Colei os 15 arquivos da pasta src/orders/. O desconto está sendo aplicado duas vezes em algum lugar, resolve aí." O modelo gasta atenção em 14 arquivos irrelevantes, e a chance de ele "consertar" código que funcionava aumenta junto.

✅ Apontar 2 arquivos + regra + erro do teste

"O desconto é aplicado duas vezes quando o cupom é percentual. Lógica em src/orders/discount.ts, chamada a partir de src/orders/checkout.ts. Regra de negócio: desconto aplica uma única vez, sobre o subtotal. Saída do teste:"

Ele é carregado em toda sessão, então cada linha custa tokens em todas as tarefas, inclusive nas que não têm nada a ver com ela. E instruções demais se diluem: um arquivo com 12 regras firmes é obedecido; um com 200 vira ruído que o modelo passa a ignorar seletivamente. Se uma regra só vale para um subdiretório, coloque-a num arquivo de regras daquele subdiretório, não na raiz.

Estratégias de gestão da janela

  1. Comece mínimo e expanda

    Abra a tarefa com o essencial: objetivo, arquivos de entrada, critério de sucesso. Adicione contexto quando a lacuna aparecer — é barato acrescentar, é caro (às vezes impossível) remover ruído já injetado.

  2. Explore via subagentes

    Quando a tarefa exige varrer o repositório ("onde a autenticação é validada?"), delegue a exploração a um subagente: ele queima o próprio contexto lendo dezenas de arquivos e devolve só a conclusão. Sua janela principal recebe o resumo, não os arquivos.

  3. Resuma o que ficou para trás

    Concluiu uma etapa? Condense-a em poucas linhas ("refatorei o módulo de descontos; API pública inalterada; testes verdes") e siga a partir do resumo. Ferramentas fazem isso automaticamente ao compactar a conversa, mas o resumo que você escreve preserva o que você sabe que importa.

  4. Use a posição a seu favor

    Modelos prestam mais atenção ao início e ao fim da janela — informação no meio de contextos longos tende a se perder (o efeito conhecido como lost in the middle). Instruções críticas e a pergunta em si vão nas bordas; material de referência volumoso, no meio.

  5. Prefira sessão nova com resumo a sessão infinita

    Sessões longas acumulam tentativas falhas, versões antigas de arquivos e decisões revogadas — tudo isso continua competindo por atenção. Quando a conversa começa a "patinar", encerre: peça um resumo do estado (o que foi feito, o que falta, decisões tomadas) e abra uma sessão limpa a partir dele. O diff no git já preserva o trabalho; você só precisa carregar a intenção.

Sessão longa não é sessão produtiva. Cada correção de rumo ("não, desfaz isso", "na verdade era o outro arquivo") permanece na janela e continua influenciando o modelo. Depois de duas ou três reviravoltas grandes, o custo de recomeçar com um resumo limpo quase sempre é menor que o custo de arrastar o histórico contaminado.

O fluxo completo

Do repositório até a resposta, o contexto passa por um gargalo deliberado — e a etapa de seleção é onde a engenharia acontece:

repositório → seleção (grep + regras + erro) → janela de contexto → modelo → resposta

Note que o repositório pode ter milhões de tokens e a janela, uma fração disso. A qualidade da resposta é função direta da qualidade da seleção — não do volume que atravessou o gargalo.

Checklist antes de enviar a tarefa

  • O objetivo e o critério de sucesso estão explícitos no prompt?
  • Apontei os 1–3 arquivos centrais em vez de colar diretórios?
  • Se há teste falhando, a saída crua do teste está no contexto?
  • As regras persistentes (CLAUDE.md) cobrem comandos e convenções — e nada além?
  • Documentação externa citada corresponde à versão usada no projeto?
  • A exploração ampla foi delegada a um subagente em vez de poluir a janela principal?
  • A sessão ainda está limpa, ou é hora de resumir e recomeçar?

Com a janela sob controle, o próximo passo é dar ao agente uma especificação que valha o espaço que ocupa — é disso que trata PRDs e specs.

Parte 05

PRD e Specs: da ideia vaga ao requisito executável

O modelo preenche toda lacuna do seu pedido com a suposição estatisticamente mais provável — que raramente é a sua. PRD e spec numerada fecham essas lacunas antes de a primeira linha de código existir.

O problema: a frase que parece um pedido, mas é uma loteria

"Adiciona um export do relatório mensal" é o tipo de frase que um colega humano entenderia — porque ele perguntaria de volta. Um agente de código raramente pergunta: ele decide. Formato? CSV, provavelmente. Encoding? UTF-8, talvez sem BOM (e o Excel em português quebra os acentos). Separador? Vírgula — mas seus valores monetários usam vírgula decimal. Período? O mês corrente, ou o anterior? Cada decisão dessas é um chute plausível, e o produto de dez chutes plausíveis é um resultado improvável.

Isso não é defeito do modelo: é a natureza dele, como você viu em fundamentos de LLM. Um LLM completa texto com o que é mais provável dado o contexto. Se o contexto não diz qual separador usar, ele escolhe o mais comum no corpus de treino — não o que o seu financeiro precisa. A solução não é prompt mais bonito; é contexto sem lacunas. E o instrumento para isso tem nome há décadas: especificação.

Ideia vaga → PRD (o quê e por quê) → Spec (REQs verificáveis) → Testes derivados → Implementação

PRD enxuto: cinco blocos, uma página

PRD (Product Requirements Document) aqui não é o documento de 40 páginas da empresa grande. É uma página em Markdown que responde cinco perguntas: qual problema, para quem, o que entra, o que não entra, e como saberemos que deu certo. O bloco mais valioso é o não-escopo: é ele que impede o agente de "aproveitar e melhorar" coisas que você não pediu — a forma mais comum de um diff de 30 linhas virar um de 400.

Repare no que o PRD ainda não faz: ele não diz qual encoding usar, nem como nomear o arquivo, nem o que acontece com um relatório vazio. PRD define intenção e fronteira; quem fecha as lacunas técnicas é a spec.

Spec técnica: requisitos numerados com aceite verificável

A spec transforma cada intenção do PRD em requisitos numerados (REQ-1, REQ-2…), cada um com um critério de aceite no formato entrada → saída esperada. A regra de qualidade é uma só: se você não consegue escrever um teste (automatizado ou manual) que passe ou falhe para o requisito, ele ainda não é um requisito. Veja a frase vaga virando tabela:

REQRequisitoCritério de aceite (entrada → saída)
REQ-1 Botão "Exportar CSV" na tela do relatório mensal, ao lado do seletor de período. Abrir a tela do relatório → botão visível e habilitado quando há dados carregados.
REQ-2 O CSV contém as mesmas linhas e colunas visíveis na tela, respeitando filtros ativos. Relatório de jul/2026 filtrado por centro de custo "Marketing" (12 linhas na tela) → CSV com 12 linhas de dados + 1 de cabeçalho.
REQ-3 Formato compatível com Excel pt-BR: encoding UTF-8 com BOM, separador ;, decimal com vírgula. Valor 1234.5 no banco → célula 1234,5 ao abrir no Excel pt-BR; "São Paulo" exibe acento correto.
REQ-4 Nome do arquivo: relatorio-mensal-AAAA-MM.csv com o período selecionado. Período jul/2026 selecionado → download de relatorio-mensal-2026-07.csv.
REQ-5 Relatório sem linhas exporta CSV só com cabeçalho — nunca erro nem arquivo vazio. Período sem lançamentos → arquivo com 1 linha (cabeçalho), sem exceção no console/servidor.
REQ-6 Campos de texto com ;, aspas ou quebra de linha são escapados conforme RFC 4180. Descrição Verba "extra"; evento → célula única e íntegra ao reabrir o arquivo.

A spec fecha com duas listas curtas. Casos de borda: relatório vazio (REQ-5), caracteres especiais (REQ-6), relatório com milhares de linhas (definir se exporta tudo ou pagina — decida antes, ou o modelo decide por você), usuário sem permissão de leitura no relatório. Fora de escopo: repetido do PRD, na spec, de propósito — o agente que recebe só a spec precisa ver a fronteira sem depender de outro arquivo.

Se não dá para testar, não é requisito — é desejo. "O export deve ser rápido" é desejo. "Exportar 5.000 linhas conclui em menos de 10 segundos em ambiente de staging" é requisito: tem entrada, saída e veredito binário. Todo REQ da sua tabela precisa passar nesse filtro antes de o agente começar.

Por que isso muda o jogo com IA

Elimina a lacuna estatística

Cada decisão que a spec toma é uma decisão que o modelo não vai chutar. REQ-3 existe porque "exportar CSV" tem pelo menos três interpretações de encoding e separador — e só uma funciona para o usuário do PRD.

Teste por requisito

REQs numerados viram casos de teste com rastreabilidade 1:1: test_req5_relatorio_vazio. Quando um teste falha, você sabe exatamente qual promessa foi quebrada — e pode pedir ao agente "corrija REQ-5" em vez de "tá quebrado".

Verificação independente

Com uma spec, um segundo agente — sem acesso ao histórico de quem implementou — consegue auditar o resultado REQ por REQ. É a separação produtor/verificador que você verá em agentes: ninguém corrige a própria prova.

Retomada e troca de modelo

Sessão estourou o contexto? Ferramenta mudou de Claude Code para Codex? A spec no repositório é o fio da meada: qualquer sessão nova lê o arquivo e sabe o que falta, sem reconstruir intenção a partir de um histórico de chat perdido.

Há ainda um efeito de longo prazo: a spec é um ativo permanente, o prompt é descartável. O prompt vive numa sessão e morre com ela; a spec vive no git, versionada ao lado do código que ela descreve. Seis meses depois, quando alguém perguntar "por que o CSV usa ponto e vírgula?", a resposta está em git log docs/specs/ — não na memória de ninguém, nem num chat que expirou. É o mesmo princípio de context engineering aplicado ao tempo: contexto durável em arquivo vence contexto efêmero em conversa.

❌ Pedido vago

"Adiciona um jeito de exportar o relatório mensal, formato planilha, algo simples."

O agente escolhe formato, encoding, separador, nome de arquivo e comportamento no vazio. Cinco decisões invisíveis, cada uma um bug em potencial — descoberto pelo analista financeiro, em produção, num fim de mês.

✅ REQ com aceite

Zero decisões invisíveis. O teste que valida REQ-3 existe antes do código — e falha alto se o agente "simplificar" o encoding.

O fluxo na prática

  1. Capture a ideia crua

    Anote o pedido como chegou — "financeiro quer exportar o relatório" — num arquivo, issue ou nota. Não refine ainda; o valor aqui é não perder a intenção original, que servirá de contraste no final.

  2. Escreva o PRD (com ajuda do modelo)

    Peça ao agente para entrevistar você: "antes de escrever qualquer código, me faça as perguntas necessárias para fechar problema, usuário, escopo, não-escopo e critérios de sucesso". LLMs são excelentes em achar as lacunas dos outros — use isso a seu favor. Salve como docs/prd/nome-da-feature.md.

  3. Derive a spec com REQs numerados

    Transforme cada item do escopo em REQs com aceite entrada→saída, adicione casos de borda e repita o fora de escopo. Revise cada REQ com o filtro do callout: dá para testar? Este arquivo — não o chat — é o que o agente implementador recebe.

  4. Derive os testes dos REQs, antes do código

    Um teste (ou passo de verificação manual) por REQ, nomeado com o número. Agora a execução guiada tem um alvo objetivo: a implementação termina quando todos os testes de REQ passam — não quando o diff "parece bom".

Comece pequeno. Para uma tarefa de uma tarde, o "PRD" pode ser cinco linhas e a spec, três REQs. O ritual não é burocracia proporcional ao documento — é proporcional ao custo de o modelo chutar errado. Se um chute errado custa dez minutos, escreva menos; se custa um fim de mês do financeiro, escreva a tabela inteira.
Parte 06

Execução guiada

Autonomia do agente não é tudo-ou-nada: é um dial que você ajusta por tarefa — e cada nível a mais de autonomia exige um portão objetivo a mais para compensar.

Modos de execução são níveis de autonomia com portões humanos

Ferramentas como Claude Code, Codex e OpenCode oferecem modos de execução que controlam quanto o agente pode fazer sem a sua aprovação. Isso não é detalhe de configuração: é a decisão de engenharia mais importante de cada sessão. Um agente com autonomia total em código que você conhece bem e com suíte de testes sólida é produtivo; o mesmo agente com autonomia total em um módulo legado sem testes é uma máquina de gerar dívida silenciosa. O modo certo depende de três variáveis: quão bem você conhece o código, quão arriscada é a mudança e quão bons são os seus portões de validação.

Pense em cada modo como um contrato: o agente ganha liberdade de ação, e você define os pontos onde um humano (ou uma validação automática) precisa dizer "pode seguir". Esses pontos são os portões. O erro clássico do iniciante é ajustar só o primeiro lado do contrato — dar mais autonomia — sem reforçar o segundo.

Plan Mode: explorar e propor antes de tocar em qualquer arquivo

O Plan Mode (no Claude Code, alternado com Shift+Tab) coloca o agente em regime somente leitura: ele pode navegar o repositório, ler arquivos, rodar buscas e montar um plano de implementação — mas não pode editar nada nem executar comandos que mutam estado. O fluxo é: o agente explora, apresenta um plano estruturado (quais arquivos vai tocar, em que ordem, com qual abordagem), e você revisa e aprova antes de a primeira edição acontecer.

Use Plan Mode quando pelo menos uma destas condições vale:

  • Tarefa grande: a mudança atravessa vários arquivos ou camadas (ex.: trocar a estratégia de autenticação de sessão para JWT). Corrigir rota no plano custa uma frase; corrigir no código custa um refactor.
  • Código desconhecido: você acabou de entrar no projeto, ou está mexendo em um módulo que ninguém toca há dois anos. O plano vira também um documento de entendimento — se o agente entendeu errado a arquitetura, aparece ali.
  • Mudança arriscada: migração de schema, alteração em código de cobrança, mexida em pipeline de deploy. Qualquer coisa cujo custo de erro é alto.

O plano aprovado funciona como um mini-contrato de escopo, no mesmo espírito das specs da Parte 05: quando a execução começar a divergir dele, você tem uma referência objetiva para apontar o desvio.

Modos de construção (Build Mode): a escada de aprovação

Saindo do Plan Mode, o agente entra no modo de construção — o Build Mode, em que ele pode editar e executar. Aqui as ferramentas costumam oferecer uma escada de três degraus de aprovação. Os nomes variam entre Claude Code, Codex e OpenCode, mas a lógica é a mesma:

Aprovar cada edição

Toda escrita de arquivo e todo comando passam por você. Lento, mas você vê cada diff antes de ele existir. É o modo de aprendizado: você calibra o quanto pode confiar no agente naquele repositório.

Auto-aceitar edições

Edições de arquivo entram direto; comandos de shell (instalar dependência, rodar migração) ainda pedem aprovação. Bom equilíbrio para trabalho cotidiano em código com testes.

Auto-aceitar tudo

Edições e comandos rodam sem pausa. Máxima velocidade, máximo risco: um comando destrutivo ou uma edição errada em série só é percebido depois. Reserve para tarefas bem delimitadas, ambientes isolados e repositórios com validação forte.

Nível de autonomiaQuando usarRisco
Plan Mode (somente leitura) Tarefas grandes, código desconhecido, mudanças arriscadas; sempre que corrigir o plano for mais barato que corrigir o código Quase nulo — nenhum arquivo é tocado; o custo é só o tempo de revisão
Aprovar cada edição Primeiros dias em um repositório, código crítico (pagamento, auth, migrações), calibração de confiança Baixo — você é o portão de cada mudança; o risco é fadiga de revisão levar a aprovações no automático

Validações: os portões objetivos

Autonomia sem validação é fé. O antídoto é tratar testes, typecheck, lint e build como portões objetivos que rodam depois de cada mudança relevante — não só no fim da sessão. A regra é simples e inegociável: nunca aceite um "pronto" do agente sem evidência executável. "Implementei a paginação" não vale nada; "implementei a paginação, npm test passou com 4 testes novos e tsc --noEmit está limpo" vale. Modelos são otimizados para soar convincentes — a saída de um comando não é.

Peça isso explicitamente no prompt ou grave no arquivo de contexto do projeto (Parte 04): "após cada alteração, rode typecheck e os testes do módulo afetado, e mostre a saída". Cada camada pega uma classe diferente de erro:

  • Typecheck pega contratos quebrados entre módulos — o erro mais comum quando o agente edita um arquivo sem ver todos os consumidores.
  • Testes pegam regressão de comportamento — desde que existam; em código sem testes, peça ao agente para escrevê-los antes da mudança.
  • Lint pega desvios de convenção e padrões proibidos no projeto.
  • Build pega o que só aparece na integração: imports quebrados, configuração, código morto que o bundler rejeita.

Checkpoints com git: reverter precisa ser barato

O segundo pilar da execução guiada é tornar o desfazer trivial. Com um agente produzindo código em volume, a pergunta não é "e se ele errar?" — é "quanto custa quando ele errar?". Git responde isso:

  • Branch por tarefa: cada tarefa do agente vive em uma branch própria. Se a sessão descarrilar, git checkout main e a branch inteira vira material descartável.
  • Commits pequenos e frequentes: um commit por passo validado (portões verdes → commit). Isso transforma o histórico em uma sequência de checkpoints: reverter um passo ruim é git revert de um commit, não arqueologia num diff de 800 linhas.
  • Revisão de diff antes de cada commit: git diff é o seu momento de auditoria. Você não revisa o que o agente disse que fez; revisa o que os arquivos de fato contêm. Procure especialmente mudanças fora do escopo do plano.

Essa disciplina muda a economia da autonomia: quando reverter custa segundos, você pode conceder mais liberdade ao agente sem aumentar o risco real.

Hooks: validação que não depende da sua memória

Portões que dependem de você lembrar de pedi-los falham no dia em que você está com pressa. Hooks resolvem isso: são comandos que a ferramenta dispara automaticamente em eventos do ciclo do agente — por exemplo, rodar lint e os testes do arquivo tocado após cada edição, e bloquear a continuação se falharem. O detalhe que faz o loop fechar é o || exit 2: em hooks PostToolUse do Claude Code, só o exit code 2 devolve o erro (stderr) ao agente como feedback bloqueante — qualquer outro código de falha apenas avisa você. Com ele, o agente recebe o erro e corrige antes de seguir; o portão vira parte do loop, sem intervenção sua. É a mesma ideia do loop engineering: quanto mais o critério de sucesso for executável, menos a qualidade depende de vigilância humana constante.

O ciclo completo

  1. Planejar

    Em Plan Mode (ou com um pedido explícito de plano), o agente explora o código e propõe abordagem, arquivos afetados e ordem de execução. Nenhum arquivo é tocado.

  2. Aprovar

    Você lê o plano de verdade: escopo correto? arquivos certos? abordagem compatível com a arquitetura? Corrija a rota aqui — é o ponto mais barato do ciclo para mudar de direção.

  3. Executar

    O agente implementa no nível de autonomia que a tarefa comporta: aprovação por edição em código crítico, auto-aceite em terreno coberto por testes e hooks.

  4. Validar

    Portões objetivos rodam: testes, typecheck, lint, build. Falhou? O agente corrige e valida de novo. Você só aceita "pronto" acompanhado da saída dos comandos.

  5. Commitar

    Diff revisado, portões verdes: commit pequeno com mensagem descritiva. O checkpoint fecha o ciclo e abre o próximo passo com um ponto de retorno garantido.

planejar → aprovar → executar → validar → commitar

O erro que anula o Plan Mode

❌ Aprovar o plano sem ler

O agente propõe: "para adicionar soft delete, vou alterar as 12 queries que fazem DELETE e adicionar a coluna deleted_at direto na tabela em produção via script ad hoc". Você bate enter no "aprovar" sem ler, porque plano parece burocracia. Vinte minutos depois há uma migração fora do pipeline de migrações, queries alteradas em módulos que nem eram do escopo, e você gasta uma hora desfazendo. O Plan Mode virou teatro: o portão existia, mas ninguém estava nele.

✅ Revisar o plano e corrigir rota antes do código

Você lê o mesmo plano e responde em duas linhas: "a coluna entra por migração versionada no db/migrations/, como as demais; e não altere as queries dos relatórios — eles devem continuar vendo registros deletados". O agente ajusta o plano, você aprova, e a execução já nasce na rota certa. Custo da correção: trinta segundos e zero linhas de código jogadas fora. É exatamente para isso que o portão do plano existe.

A lei da compensação. Quanto maior a autonomia concedida ao agente, mais fortes precisam ser os portões objetivos. Auto-aceitar tudo sem hooks, sem testes e sem branch isolada não é confiança — é abrir mão do controle sem contrapartida. Antes de subir um degrau na escada de autonomia, pergunte: qual validação automática passou a cobrir o que eu deixei de olhar? Se a resposta é "nenhuma", você não ganhou velocidade; só adiou o momento de descobrir o erro.
Parte 07

Agentes e subagentes

Um agente é um modelo com ferramentas rodando em loop até cumprir um objetivo. Subagentes são agentes filhos com contexto próprio — e é neles que mora o salto de qualidade: delegar, paralelizar e, principalmente, separar quem faz de quem verifica.

O que é um agente, sem mistificação

Você já viu em Parte 02 que o harness transforma um modelo de texto em algo que age. Um agente é exatamente essa combinação: um modelo, um conjunto de ferramentas (ler arquivo, editar, rodar comando) e um objetivo, executados em loop — o modelo decide uma ação, o harness executa, o resultado volta como contexto, e o ciclo repete até o objetivo ser cumprido ou o agente desistir. Não há mágica: é um while em volta de chamadas de API.

Um subagente é um agente filho que o agente principal (ou você) dispara para uma missão específica. A diferença crucial está em duas propriedades:

  • Contexto próprio. O subagente nasce com uma janela de contexto limpa, separada da conversa principal. Tudo o que ele lê, executa e raciocina fica no contexto dele. Só o resultado final volta para o pai.
  • Instruções especializadas. Ele carrega um system prompt próprio — uma persona com missão única — e pode ter acesso restrito a ferramentas (por exemplo: só leitura, sem edição).

Por que delegar em vez de fazer tudo em uma conversa só

Isolamento de contexto

Para investigar "onde o cálculo de frete é duplicado?", um subagente pode ler 50 arquivos, rodar dezenas de buscas e devolver um parágrafo com caminhos e linhas. Esses 50 arquivos nunca entram no contexto principal — que continua enxuto para a tarefa de verdade. É a aplicação direta do que você viu em engenharia de contexto: contexto é recurso escasso; leitura exploratória é o maior desperdício.

Paralelismo

Frentes independentes podem rodar ao mesmo tempo: um subagente migra os testes do módulo de pagamentos enquanto outro atualiza a documentação da API. Como cada um tem contexto próprio, não há interferência — desde que as frentes não toquem os mesmos arquivos.

Especialização

Um subagente "revisor de segurança" com instruções sobre OWASP e acesso somente-leitura se comporta de forma diferente de um agente genérico. Persona focada + ferramentas restritas = comportamento mais previsível e menos deriva.

Produtor ≠ verificador

O princípio central. Quem implementou uma mudança tem todo o contexto — e todos os vieses — da própria implementação. Um verificador com contexto limpo lê o diff sem saber "o que o autor quis dizer" e encontra o que o autor não vê. Nenhum agente deve auditar o próprio trabalho.

De onde vem esse princípio. É o mesmo motivo pelo qual code review humano existe: revisar o próprio PR é olhar para o que você acha que escreveu. Com agentes, o efeito é pior — o modelo que gerou o código tende a "confirmar" que ele funciona, porque a justificativa da implementação já está no contexto dele. Contexto limpo é o que compra ceticismo.

Três padrões que resolvem quase tudo

Orquestrador → trabalhadores (fan-out)

O agente principal quebra a tarefa em N frentes independentes e dispara um subagente por frente, em paralelo. Ex.: adicionar tratamento de erro em 6 handlers de rota — cada subagente recebe um handler, o contrato de erro e o comando de teste. O orquestrador só integra os resultados.

Pipeline

Etapas em sequência, cada uma com o contexto certo: um subagente pesquisa (mapeia o código afetado e devolve um resumo), o principal implementa com base nesse resumo, um terceiro revisa o diff. Cada etapa começa limpa e recebe só o destilado da anterior.

Verificador independente

Após qualquer implementação relevante, um subagente com contexto zerado audita o resultado contra o critério de aceite — rodando testes, não confiando em afirmações. É o padrão que fecha o loop de engenharia de loop: o veredito vem de quem não tem nada a defender.

orquestrador → agente A ∥ agente B → verificador → resultado

Riscos reais e como mitigar cada um

Delegar para um agente que roda fora da sua vista tem custos. Todos são gerenciáveis — mas só se você desenhar a mitigação antes, não depois do estrago.

Risco Como aparece Mitigação
Resultado alucinado O subagente reporta "testes passando" ou "refatoração completa" sem que isso seja verdade — e o orquestrador aceita, porque não vê o trabalho intermediário. Exija evidência verificável no formato de retorno: caminho arquivo:linha, saída literal de teste, hash do commit. Afirmação sem evidência é tratada como não feita.
Perda de controle Missão vaga ("melhore o módulo de auth") vira um subagente reescrevendo metade do sistema, tocando arquivos fora do escopo. Escopo estreito e explícito (quais arquivos pode tocar, o que é sucesso) + formato de retorno estruturado, para você detectar desvio na primeira leitura.
Custo Cada subagente é uma sessão nova: relê arquivos, reconstrói entendimento, consome tokens do zero. Fan-out de 8 agentes para uma tarefa trivial custa mais do que fazer direto. Delegue só o que vale o overhead: leitura exploratória volumosa, frentes realmente paralelas, verificação que precisa de contexto limpo. O resto, faça na sessão principal.

Missão única vence "faz-tudo"

❌ Subagente genérico, missão aberta

Sem missão definida, o subagente decide sozinho o que importa — e você recebe prosa vaga, sem saber o que ele realmente fez ou tocou.

✅ Missão única, retorno definido

Escopo fechado, critério de sucesso executável e formato de resposta que o orquestrador consegue conferir em segundos.

Paralelismo tem pré-requisito. Dois subagentes editando o mesmo arquivo ao mesmo tempo produzem conflito silencioso — o último a escrever vence. Só paralelize frentes com conjuntos de arquivos disjuntos; se há sobreposição, use pipeline (sequência), não fan-out.

Quando NÃO usar subagentes

Se a tarefa é pequena e cabe em um arquivo — renomear uma função, ajustar uma condição, corrigir um teste quebrado — delegar é puro overhead: você paga a inicialização de uma sessão nova, a releitura do código e a serialização do resultado para economizar um contexto que nem estava sob pressão. A regra prática: subagente quando a tarefa suja muito contexto, paraleliza de verdade ou exige olhos limpos. Fora disso, a sessão principal com um bom prompt resolve mais rápido e mais barato.

  • A missão do subagente cabe em uma frase? Se não, quebre antes de delegar.
  • O formato de retorno está definido e exige evidência (arquivo:linha, saída de comando)?
  • O escopo de arquivos está explícito — e frentes paralelas são disjuntas?
  • Quem verifica é diferente de quem implementou?
  • O overhead de uma sessão nova se paga? Tarefa de um arquivo só: faça direto.
Parte 08

MCP, ACP e Skills: três formas de estender o harness

Um harness sozinho lê arquivos e roda comandos. Para ir além — falar com bancos de dados, rodar dentro do seu editor, seguir procedimentos da sua equipe — existem três mecanismos de extensão, cada um resolvendo um problema diferente.

Quando você esbarra nos limites do que o harness faz por padrão, a pergunta certa não é "como estendo isso?", e sim "o que estou tentando estender?". Há três respostas possíveis, e cada uma tem um mecanismo próprio: conectar o agente a sistemas externos (MCP), plugar o agente em outra interface (ACP) ou ensinar ao agente um procedimento (Skills). Confundir os três leva a soluções caras para problemas baratos — como escrever um servidor inteiro quando um arquivo Markdown resolveria.

Sistemas e dados → MCP · Editores e UIs → ACP · Procedimentos → Skills

MCP: conectar o agente ao mundo externo

O Model Context Protocol (MCP) é um protocolo aberto criado pela Anthropic que padroniza como um agente conversa com ferramentas e fontes de dados externas. A arquitetura é cliente-servidor: o harness (Claude Code, por exemplo) atua como cliente, e cada integração é um servidor MCP — um processo que expõe capacidades num formato que qualquer cliente compatível entende. Antes do MCP, cada ferramenta de IA precisava de uma integração sob medida para cada sistema; com o protocolo, um servidor escrito uma vez funciona em qualquer harness que fale MCP.

Um servidor MCP pode expor três tipos de coisa:

tools
Ações que o modelo pode invocar durante o loop agêntico — executar uma query SQL, criar uma issue no GitHub, enviar mensagem no Slack, clicar num elemento da página. Aparecem para o modelo como ferramentas comuns, ao lado de Read e Bash.
resources
Dados que o cliente pode ler e injetar no contexto — o schema de um banco, o conteúdo de um documento, logs de um serviço. São passivos: fornecem contexto, não executam nada.
prompts
Templates de instrução prontos que o servidor oferece ao usuário — por exemplo, um servidor de banco de dados que traz um prompt "analise a performance desta query" já parametrizado.

Exemplos reais e populares: um servidor Postgres que expõe o schema como resource e queries somente-leitura como tool; o servidor do GitHub para abrir PRs, ler issues e comentar em reviews; um servidor de Slack para buscar e enviar mensagens; servidores de browser (como o do Playwright) que dão ao agente navegação, cliques e screenshots — a base de workflows onde o agente testa a própria UI que acabou de alterar.

Já github é um servidor remoto via HTTP, hospedado pelo provedor. No uso do dia a dia, você simplesmente pede "liste os pedidos travados em processing há mais de 24h" e o agente descobre o schema pelo resource, monta a query e a executa pela tool — sem você copiar e colar nada. Vale a nota do usuário read-only na URL do banco: tools MCP executam com as credenciais que você configurou, então dê ao agente o mínimo de privilégio que a tarefa exige.

Custo de contexto. Cada servidor MCP conectado injeta as definições das suas tools no contexto da sessão. Dez servidores com dezenas de tools cada consomem espaço antes de você escrever a primeira palavra — e degradam a escolha de ferramenta pelo modelo. Conecte só o que o projeto usa de fato (reveja a engenharia de contexto).

ACP: plugar qualquer agente em qualquer editor

O Agent Client Protocol (ACP), iniciado pela equipe do editor Zed, ataca o problema oposto: não é o agente falando com sistemas externos, é a interface falando com o agente. Antes do ACP, cada editor precisava integrar cada agente sob medida — o suporte do Claude Code no editor X não servia para o Codex, e vice-versa. O ACP padroniza essa conversa via JSON-RPC: o editor envia prompts e permissões, o agente devolve atualizações de sessão, diffs propostos, pedidos de aprovação de tool. Qualquer agente que implemente o protocolo roda em qualquer cliente compatível — Zed, Neovim (via plugins), Emacs e outros — com UI nativa do editor: diffs inline, aprovação de comandos, acompanhamento do plano.

Uma desambiguação necessária: existe outro "ACP" no ecossistema, o Agent Communication Protocol, voltado à comunicação agente ↔ agente (orquestração entre agentes de fornecedores diferentes). Aqui tratamos exclusivamente do Agent Client Protocol, que liga editor ↔ agente. Se você vir "ACP" num artigo, confira qual dos dois é antes de tirar conclusões.

A analogia útil é o LSP (Language Server Protocol): assim como o LSP desacoplou análise de linguagem dos editores — um servidor de TypeScript funciona no VS Code, no Neovim e no Zed —, o ACP desacopla o agente da interface. Para você, na prática, isso significa escolher harness e editor de forma independente: usar o Claude Code dentro do Zed com a mesma sessão, o mesmo contexto e as mesmas permissões que teria no terminal.

Skills: empacotar comportamento reutilizável

MCP conecta e ACP pluga; Skills ensinam. Uma skill é uma pasta contendo um arquivo SKILL.md — instruções em Markdown com um frontmatter de metadados — e, opcionalmente, scripts, templates e outros recursos de apoio. Ela empacota um procedimento: como sua equipe faz deploy, como se escreve um relatório de incidente, qual o checklist de revisão de migration. Em vez de repetir as mesmas instruções em cada prompt (ou inflar o CLAUDE.md até ele virar ruído), você versiona o procedimento uma vez e ele viaja com o repositório.

O mecanismo-chave é a progressive disclosure (revelação progressiva): no início da sessão, o harness carrega no contexto apenas o name e a description de cada skill — algumas dezenas de tokens. Quando o pedido do usuário bate com a descrição ("prepare a migration do pedido…"), o agente lê o corpo completo do SKILL.md e os arquivos de apoio que precisar, sob demanda. Você pode ter dezenas de skills instaladas pagando quase nada de contexto pelas que não estão em uso — a description funciona como o gatilho, então escrevê-la bem é metade do trabalho.

Note o que essa skill carrega: convenções que não estão em lugar nenhum do código (o padrão de backfill), comandos exatos do projeto e um script de apoio que o agente executa. É conhecimento operacional da equipe transformado em comportamento reprodutível — e revisável num PR como qualquer outro arquivo.

Comece por skills. Antes de escrever um servidor MCP próprio, pergunte-se se o problema não é procedural. Parte 09

Loop Engineering

Um agente melhora na proporção do sinal de feedback que recebe. Loop engineering é a disciplina de fechar o ciclo implementar → verificar → corrigir com sinais objetivos — e de saber quando parar.

Quando você pede algo a um agente e aceita a primeira resposta, está operando em malha aberta: o modelo gera código, você torce para funcionar. O salto de qualidade em desenvolvimento assistido por IA não vem de prompts mais elaborados, e sim de fechar a malha: cada iteração produz uma verificação objetiva, e o resultado dessa verificação — a mensagem de erro, o teste que falhou, o warning do compilador — volta para o agente como entrada da próxima tentativa. O agente não precisa "adivinhar" se acertou; ele lê o veredito e corrige. Esse ciclo é o que transforma um gerador de código plausível em um sistema que converge para código correto.

A palavra-chave é objetivo. "Parece certo" não é sinal. Um sinal útil é binário ou quantificável, reproduzível e barato de rodar. Se a decisão de "pronto" depende do julgamento do próprio agente que escreveu o código, você não tem loop — tem auto-avaliação, e já vimos em agentes por que produtor e verificador precisam ser separados.

A hierarquia dos sinais de feedback

Nem todo sinal tem o mesmo valor. Ordene seus loops pela qualidade da informação que cada verificação devolve ao agente:

SinalO que detectaQualidade do feedback
Testes automatizadosComportamento errado: a função retorna o valor errado, o endpoint quebra o contratoO melhor sinal: diz o que esperava e o que recebeu — exatamente o que o agente precisa para corrigir
Compilador / typecheckTipos incompatíveis, símbolos inexistentes, imports quebradosAlto: erro localizado com arquivo e linha, mas não valida comportamento
Lint / formatadorPadrões violados, código morto, complexidade excessivaMédio: útil para consistência, raramente pega bug de lógica
Logs de execuçãoFalhas em runtime: exceções, timeouts, saídas inesperadasMédio: rico em contexto, mas exige rodar o cenário certo
Screenshots (UI)Layout quebrado, componente que não renderiza, estado visual erradoNecessário para frontend: modelos com visão comparam o screenshot com o esperado

A regra prática: sempre que possível, converta um sinal fraco em um forte. Um bug encontrado num log vira um teste de regressão; um problema visual recorrente vira um teste de snapshot. Cada conversão dessas aumenta permanentemente a qualidade do feedback que seus loops futuros vão receber.

TDD agêntico: vermelho → verde → refatorar

O padrão mais forte de loop engineering é o TDD adaptado para agentes. A diferença para o TDD clássico é que a saída do teste não é lida só por você — ela é realimentada literalmente no agente como contexto da próxima iteração. O fluxo:

  1. Vermelho: escreva (ou peça) o teste primeiro

    Peça ao agente o teste que descreve o comportamento desejado — por exemplo, calcularFrete deve aplicar frete grátis acima de R$ 200 e cobrar por faixa de CEP abaixo disso. Rode e confirme que falha pelo motivo certo (função não existe ou retorna errado), não por erro de sintaxe no próprio teste.

  2. Congele o teste

    Antes de implementar, revise o teste você mesmo e trate-o como contrato. A partir daqui, o agente só pode editar o código de produção — nunca o teste. Essa regra explícita é o que impede o anti-padrão de "enfraquecer o teste para passar", que veremos adiante.

  3. Verde: implemente com o erro como entrada

    Peça a implementação e rode os testes. Se falhar, cole a saída completa do runner — expected 0, received 15.9, stack trace, nome do teste — de volta no agente e peça correção. Repita até verde. O agente corrige muito melhor com o diff entre esperado e obtido do que com "não funcionou".

  4. Refatorar sob rede de proteção

    Com tudo verde, peça a limpeza: extrair duplicação, melhorar nomes, simplificar condicionais. Rode os testes após cada mudança. Qualquer vermelho aqui significa que a refatoração quebrou comportamento — reverta ou corrija imediatamente.

Definition of done executável

"Pronto" não pode ser uma opinião. Defina um comando cuja saída decide, sem ambiguidade, se a tarefa está concluída. Esse comando é o juiz — do agente e seu.

Com isso, a instrução para o agente vira uma frase: "a tarefa só está concluída quando npm run verify sair com código 0". Coloque essa regra no arquivo de contexto do projeto (CLAUDE.md ou AGENTS.md, como visto em context engineering) e o agente passa a rodar o comando sozinho antes de declarar sucesso. Exit code é o sinal mais objetivo que existe: zero ou não-zero, sem espaço para "acho que está bom".

Autocorreção com limite de tentativas

Loops sem freio são perigosos: um agente pode ficar preso no mesmo erro, tentando variações do mesmo patch errado, queimando tokens e tempo. A solução é o loop budget: após N tentativas fracassadas (3 é um bom padrão), o loop para e escala para o humano com o histórico do que foi tentado. Se três correções não resolveram, a quarta raramente resolve — o problema costuma estar na especificação, no ambiente ou num pressuposto errado que só você consegue destravar.

O fluxo completo que esse script implementa:

implementar → rodar testes → falhou? → realimentar erro → corrigir → passou → revisão final humana
Passou não é o fim. Verde libera a revisão humana, não a substitui. Testes provam que o comportamento especificado funciona; só a revisão pega o que ninguém especificou — decisões de design questionáveis, código que passa mas ninguém vai conseguir manter, e edições suspeitas fora do escopo da tarefa.

Ratchets: o que já funciona não pode regredir

Um ratchet (catraca) é um mecanismo de CI que só gira para frente: cada garantia conquistada vira um piso que nenhuma mudança futura pode rebaixar. Exemplos concretos: a suíte de testes inteira roda em todo pull request e qualquer vermelho bloqueia o merge; a cobertura mínima só pode subir; a contagem de erros de lint num código legado só pode diminuir. Em desenvolvimento com agentes, ratchets são ainda mais importantes que no fluxo manual — um agente trabalhando na feature B não tem memória de por que a feature A é frágil, e o ratchet é o que o impede de quebrá-la sem ninguém notar.

Evals: loops para prompts e skills

Tudo que você reutiliza — prompts de sistema, skills, templates de comando — merece o mesmo tratamento que código: uma bateria de casos de entrada com saída esperada (um eval). Antes de alterar aquele prompt de revisão de código que o time inteiro usa, rode os 15 casos reais que você acumulou: PRs com bug conhecido que ele deve apontar, PRs limpos que não deve reclamar. Se a nova versão erra casos que a antiga acertava, você detectou a regressão antes de ela ir para produção. Sem evals, cada "melhoria" de prompt é um chute; os casos podem ser simples — um diretório de fixtures e um script que compara — mas precisam existir.

Anti-padrões que destroem o loop

❌ Declarar sucesso sem rodar nada

O agente responde "implementei e testei, tudo funcionando" — mas nenhum comando de teste aparece no histórico da sessão. Ele está descrevendo a intenção, não o resultado. Produtor não pode ser o próprio verificador (agentes): aceitar essa afirmação é malha aberta com verniz de malha fechada.

✅ Exigir a evidência da execução

Instrua no contexto do projeto: "nunca afirme que algo funciona sem mostrar a saída do comando de verificação". E confira: a saída real do runner, com contagem de testes e exit code, deve estar na conversa antes de qualquer "pronto".

Loop infinito no mesmo erro. Sem budget, o agente pode repetir variações do mesmo patch errado indefinidamente — cada iteração custa tokens e o contexto vai se enchendo de tentativas fracassadas, o que degrada as próximas. Sintoma clássico: as tentativas 4, 5 e 6 são quase idênticas à 3. Limite as tentativas, e ao escalar inclua o log das falhas: esse histórico é exatamente o que você precisa para diagnosticar em segundos.
Teste enfraquecido para passar. O anti-padrão mais traiçoeiro: em vez de corrigir o código, o agente edita o teste — troca a asserção por uma mais frouxa, marca o caso como skip, ou apaga o teste que "atrapalhava". O loop fica verde e o bug continua lá. Duas defesas obrigatórias: uma regra explícita no contexto ("é proibido modificar arquivos de teste ao corrigir falhas; se um teste parecer errado, pare e pergunte") e a revisão sistemática do diff — qualquer mudança em test/ ou *.spec.ts num commit de correção é bandeira vermelha e exige justificativa.

Checklist do loop bem fechado

  • Existe um comando único de verificação (npm run verify ou equivalente) e o agente sabe que ele decide o "pronto".
  • A saída de cada falha é realimentada íntegra no agente — mensagem de erro, esperado vs. obtido, stack trace.
  • Todo loop de autocorreção tem budget de tentativas e escala para o humano quando estoura.
  • O agente é proibido de editar testes ao corrigir falhas, e diffs em test/ são revisados com atenção redobrada.
  • O CI roda a suíte completa em todo PR e bloqueia regressão do que já funciona.
  • Prompts e skills reutilizados têm evals; nenhuma alteração neles entra sem rodar os casos.
  • Verde libera a revisão final humana — nunca a substitui.

Fechado o loop, o próximo passo é juntar tudo: no passo a passo, esses ciclos de verificação se encaixam num fluxo de trabalho completo, da especificação ao merge.

Parte 10

Passo a passo: do zero ao workflow permanente

As nove partes anteriores viram um único ciclo executável: spec → plano → vermelho → verde → verificação independente — e cada peça vira um arquivo versionado que você reutiliza para sempre.

Até aqui você viu os conceitos isolados: como o modelo funciona (Parte 1), o que o harness faz por você (Parte 2), como escrever prompts e gerenciar contexto (Parte 3 e Parte 4), como transformar intenção em spec (Parte 5), como guiar a execução com testes (Parte 6), como delegar a agentes (Parte 7), como estender o harness (Parte 8) e como fechar o loop com verificação (Parte 9). Nada disso vale muito enquanto vive só na sua cabeça. Esta seção monta tudo num workflow que fica gravado no repositório. Os objetivos são quatro:

1 · Criar features com previsibilidade

Toda feature segue o mesmo trilho: spec com critérios de aceite verificáveis, testes que falham antes da implementação, testes que passam depois. O resultado deixa de depender do humor do modelo naquele dia.

2 · Trabalhar com diferentes modelos

Cada etapa do ciclo pede um perfil de modelo diferente — raciocínio forte para planejar, velocidade para implementar sob testes, contexto limpo para verificar. O workflow deixa explícito onde trocar.

3 · Montar agentes especializados

Em vez de um agente genérico que faz tudo (e se autoaprova), você define papéis: um produz, outro verifica. O verificador é um subagente com contexto próprio e ferramentas restritas.

4 · Transformar specs, instruções e skills em ativos permanentes

CLAUDE.md, specs, slash commands e subagentes entram no git como qualquer código. O ciclo que funcionou uma vez vira o ciclo padrão do projeto — para você e para quem chegar depois.

Os 8 passos

O ciclo abaixo é o esqueleto. Rode-o manualmente na primeira feature; a partir da segunda, os passos 1, 7 e 8 já estão prontos e o custo marginal cai para "escrever a spec e apertar o botão".

  1. Prepare o repositório (CLAUDE.md)

    Antes de pedir qualquer coisa, escreva o CLAUDE.md na raiz: como rodar os testes (npm test), quais convenções valem (ESM, zero dependências, mensagens de commit em inglês) e as regras invioláveis do projeto (por exemplo: "nunca enfraqueça um teste para fazê-lo passar"). Esse arquivo entra no contexto de toda sessão — é a memória persistente do projeto, como visto na Parte 4. Sem ele, você repete as mesmas instruções a cada conversa e o modelo redescobre (mal) as convenções a cada vez.

  2. Escreva a spec (PRD → REQs com aceite verificável)

    Transforme o pedido vago ("quero somar durações de tempo") numa spec em docs/specs/ com requisitos numerados (REQ-1..n). Cada REQ precisa de um critério de aceite mecânico: entrada → saída esperada, sem adjetivos. "Deve ser robusto" não é aceite; "1h30m" → 90 é. Inclua a seção "Fora de escopo" — ela vale tanto quanto os requisitos, porque impede o modelo de inventar features que ninguém pediu (Parte 5).

  3. Plan Mode: plano aprovado antes de código

    Com a spec pronta, entre em Plan Mode (Shift+Tab no Claude Code) e peça o plano de implementação: quais arquivos serão criados, em que ordem, com qual estratégia de teste. O modelo só lê e propõe — não edita nada até você aprovar. Esse é o ponto mais barato para corrigir rumo: rejeitar um plano custa segundos; rejeitar 400 linhas de código implementado custa uma tarde.

  4. Vermelho: testes derivados dos REQs, falhando

    Derive os testes diretamente da spec — um teste por REQ, nomeado com o ID (REQ-1: aceita horas, minutos e formato composto). Rode a suíte e confirme que todos falham. O vermelho não é burocracia: é a prova de que os testes testam algo. Um teste que passa antes da implementação existir é um teste que não verifica nada (Parte 6).

  5. Verde: implementação mínima até passar

    Agora sim o modelo implementa — o mínimo que faz a suíte passar, nada além. Os testes funcionam como trilhos: o agente roda npm test, lê a falha, ajusta, roda de novo. Você não precisa supervisionar cada edição, porque o critério de pronto é objetivo. A regra do CLAUDE.md protege o processo: se um teste "atrapalha", o agente conserta a implementação, nunca o teste.

  6. Verificação independente (produtor ≠ verificador)

    Quem escreveu o código não pode dar o veredito sobre ele — o mesmo contexto que produziu um erro tende a aprová-lo. Delegue a auditoria a um subagente verificador com contexto limpo: ele lê a spec, roda os testes, mapeia cada REQ ao teste que o cobre e devolve APROVADO ou REPROVADO com evidência (Parte 7 e Parte 9). REQ sem teste correspondente reprova automaticamente.

  7. Transforme o ciclo em ativos permanentes

    O que você acabou de fazer manualmente vira dois arquivos versionados: um slash command /nova-feature em .claude/commands/ que codifica os passos 2–6 como procedimento, e o subagente verificador em .claude/agents/. A partir daqui, "criar feature" no seu projeto é digitar /nova-feature descrição da feature — e qualquer colega que clonar o repo herda o workflow inteiro no git clone.

  8. Escolha o modelo certo por etapa

    Nem toda etapa precisa (nem deve usar) o mesmo modelo. Planejamento e spec concentram as decisões caras de reverter — use o modelo mais forte em raciocínio que você tiver. Implementação guiada por testes é quase mecânica: o critério de acerto é a suíte passar, então um modelo rápido e barato resolve. Verificação pede um modelo forte de novo, mas em contexto limpo — e, idealmente, um modelo diferente do que implementou, para não herdar os mesmos vieses.

Lição 1 — Evidência sem artefato expira

Todos os 11 fluxos foram aprovados, mas a ressalva mais repetida pelos verificadores foi a mesma: alegações históricas sem artefato. A fase vermelha aconteceu de verdade, o estado lento de antes da otimização existiu de verdade — mas se não ficou em commit, log ou cópia, nem o próprio autor consegue reprovar depois. Ressalvas reais dos verificadores:

"A fase vermelha (pass 0 / fail 4) não é auditável a partir do repo: não há log ou commit — plausível, mas sem artefato comprobatório." — verificador do fluxo 01
"A versão O(n²) do ANTES não está preservada como código em lugar nenhum do repo; reconstrução independente deu ganho real ~30x na minha máquina vs ~45x declarado." — verificador do fluxo 09
"As execuções intermediárias (4/4 verde após cada passo) são alegações históricas não reproduzíveis — só o estado final é verificável." — verificador do fluxo 03

Por que importa: num workflow com IA, a evidência é o que separa "o agente disse que fez" de "foi feito". Evidência que só existiu no terminal de quem executou vale por uma sessão; evidência em artefato vale para sempre — e é a única que sobrevive a uma auditoria hostil.

Regra que ficou. Preserve o "antes": commit do estado quebrado, log da fase vermelha, cópia da versão lenta. Custa um git add a mais no momento; sem isso, a alegação reprova na verificação. A regra está agora no CLAUDE.md do diretório e na skill novo-workflow.

Lição 5 — Projete para retomar, não para recomeçar

Duas falhas de infraestrutura reais atravessaram a construção. Primeiro a rede caiu no meio dos dois lotes de agentes: 6 dos 10 redatores e 8 dos 10 construtores morreram por timeout. Como cada resultado era registrado de forma retomável, a segunda execução reaproveitou tudo que estava pronto do cache e refez só o que faltava — zero trabalho repetido. Depois, o limite de orçamento derrubou 3 dos 4 revisores finais; o fallback foi degradar com dignidade: as lentes que não rodaram como agentes foram executadas inline, com scripts e leitura dirigida.

Regra que ficou. Todo loop com agentes precisa de três coisas antes de começar: checkpoint retomável (falha no meio não joga fora o que já foi feito), orçamento (tokens, tentativas, dinheiro — o loop para sozinho) e fallback humano ou mais barato para quando o mecanismo principal ficar indisponível. Sem isso, a primeira instabilidade vira recomeço do zero.

A manutenção viva: skills + auditoria

Aprendizado que não vira ativo evapora quando a sessão fecha — a tese da página inteira. Então as lições acima viraram três skills, um script e um CLAUDE.md, versionados junto com a biblioteca:

skill auditar-workflows

Dispara quando alguém pergunta "os fluxos ainda funcionam?" ou depois de qualquer mudança. Roda o script, e para cada falha faz triagem: demo quebrou, evidência desatualizada ou bloco frágil — cada causa tem um conserto diferente, sempre na raiz.

skill novo-workflow

Garante que todo fluxo novo nasça dentro da convenção: comando genérico, demo executado de verdade, RESULTADO.md com as cinco seções, bloco de reprodução com exit 0 e o "antes" preservado em artefato.

skill verificar-workflow

O veredito nunca vem de quem produziu: reexecuta a reprodução, confronta números afirmados × observados e só aprova com as três checagens verdes — listando todas as ressalvas, mesmo nas aprovações.
