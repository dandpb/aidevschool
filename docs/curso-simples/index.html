Antes de começar · por que este curso existe

O que 10 semanas e 349 commits nos ensinaram

Este curso nasce de uma base de código real — o repositório aidevschool — que passou por um ciclo completo de construção com IA. O diagnóstico honesto desse ciclo é o melhor material didático que existe, porque cada princípio abaixo tem uma cicatriz.

📊 O ciclo em números

  • 11 engines, 16 jogos 3D, 19 projetos de currículo
  • ~92 mil linhas de documentação
  • 2 unidades de aprendizagem verificadas
  • 0 usuários externos medidos

A máquina de provar honestidade funcionou (gates, verificadores, evidência). A máquina de provar valor — alguém usando — nunca existiu.

🎯 A decisão deste curso

Recomeçar de um jeito mais simples:

  • Uma fatia vertical de ponta a ponta, não 11 frentes a 80%
  • Uma entrega usável: uma página + um workflow que qualquer aluno roda offline
  • Simplicidade como etapa obrigatória, não como intenção

Módulo 01

Fundamentos de LLMs: instruções, contexto, tokens e ferramentas

Um LLM não “entende” o seu pedido: ele continua um texto. Quase tudo que dá errado em desenvolvimento com IA vem de tratar o modelo como um colega de equipe que já sabe o contexto. Ele não sabe. Ele só vê o que está na janela de contexto — naquele instante.

1.1 — O modelo só vê texto (e só vê o que está na janela)

A cada turno, o harness monta um único texto e o envia ao modelo: system prompt + histórico da conversa + arquivos anexados + descrição das ferramentas + sua mensagem. O modelo lê tudo, gera a continuação mais provável e pronto — ele não tem memória entre conversas, não vê o seu disco e não sabe o que você quis dizer.

sua mensagem→ janela de contexto (texto montado)→ modelo gera continuação→ ferramenta executa→ resultado volta ao contexto
Consequência direta

Se uma informação não está no contexto, ela não existe para o modelo. “Eu te falei ontem” não vale: a conversa de ontem é outra janela. Por isso contexto persistente vive em arquivos (regras, specs, skills) e não no chat.

1.2 — Tokens: a unidade de medida do contexto

O texto é fatiado em tokens — pedaços de ~4 caracteres em inglês (menos em português e código). A janela de contexto é medida em tokens e tem teto. Três implicações práticas:

  • Custo e latência crescem com o tamanho do contexto — colar o repo inteiro é caro e lento.
  • Atenção dilui: quanto mais texto, menor a chance de o modelo usar um detalhe enterrado no meio. Contexto grande ≠ contexto bom.
  • Perda do meio: modelos prestam mais atenção no começo e no fim do contexto. Regras críticas vão no início; o pedido atual, no fim.
Regra prática Um contexto de 5 arquivos diretamente relacionados vence um contexto de 50 arquivos “por garantia”. Selecionar contexto é medir qualidade — é o Módulo 4 inteiro.

1.3 — Instruções: o modelo completa, não obedece

Como o modelo gera a continuação estatisticamente provável, uma instrução ambígua recebe a interpretação mais comum, não a sua. Cada campo que você omite vira uma decisão que o modelo toma sozinho — pelo caminho padrão do treinamento dele.

Ambíguo → decisão do modelo

“melhora esse código”

  • Melhor em quê? performance? legibilidade?
  • Pode reescrever a API? trocar a lib?
  • Onde estão os testes que provam?
Contrato → decisão sua

“em src/limiter.ts, troque o timer por refill lazy; não mude a interface pública; aceite: npm test verde”

1.4 — Ferramentas: como o modelo age no mundo

Sozinho, o modelo só gera texto. O harness expõe ferramentas (ler arquivo, rodar comando, buscar na web…) como descrições em texto. O fluxo vira um ciclo:

  1. O modelo decide chamar uma ferramenta e emite uma chamada estruturada (nome + argumentos).
  2. O harness executa — é código determinístico, não o modelo.
  3. O resultado (ou o erro) volta como texto para o contexto.
  4. O modelo continua com a nova informação — corrige, tenta de novo ou responde.
O ponto que muda tudo

A certeza de que algo funcionou nunca vive no modelo — vive na saída do comando que o harness executou. “Fiz e funcionou” dito pelo modelo sem saída de comando não é evidência, é continuação de texto. Este é o princípio F3 aplicado à conversa.

1.5 — O ciclo modelo → ferramenta → modelo

especificar (texto)→ modelo planeja→ ferramenta executa→ resultado no contexto→ modelo corrige ou conclui

Todo o resto do curso é sobre como governar esse ciclo: quem escolhe o plano (Módulo 6), o que entra no contexto (Módulo 4), como separar quem faz de quem verifica (Módulo 7) e como transformar cada ciclo concluído em um ativo (Módulo 9).

✏️ Exercício — sinta o problema do contexto

Em uma conversa nova, peça: “corrija o bug do rate limiter” sem anexar nada. Anote o que o modelo inventa. Depois repita com o arquivo do código + a saída do teste falhando anexados. Compare: o primeiro pedido forçou o modelo a alucinar contexto; o segundo só precisou raciocinar. Guarde essa diferença — ela é a tese do Módulo 4.

Módulo 02

Harness: o software ao redor do modelo

Claude Code, Codex e OpenCode não são modelos: são harnesses — o programa que monta o contexto, executa ferramentas, aplica permissões e gerencia a conversa. O modelo é o motor; o harness é o carro. Entender essa separação é o que permite trocar de modelo sem perder o workflow.

2.1 — O que um harness faz (as 6 responsabilidades)

ResponsabilidadeO que significaOnde você mexe
Montagem de contextoJunta system prompt + regras + histórico + arquivosCLAUDE.md, AGENTS.md, anexos
FerramentasLer/escrever arquivos, terminal, busca — com permissõesAprovações, allowlists de comando
ExecuçãoRoda o que o modelo pediu e devolve saída/erroSandbox, timeouts
Memória persistenteArquivos de regras recarregados em toda sessãoCLAUDE.md, AGENTS.md, .cursor/rules
ModosPlan (só análise) vs Build (edita) — papéis separadosShift+Tab no Claude Code, /plan etc.
ExtensibilidadeSkills, comandos slash, subagentes, MCPMódulo 8 inteiro

2.2 — O mesmo workflow em três harnesses

A anatomia é praticamente idêntica entre os harnesses de código. O que muda é nome e caminho de arquivo:

ConceitoClaude CodeCodex CLIOpenCode
Regras do projetoCLAUDE.mdAGENTS.mdAGENTS.md
Modo planoShift+Tab / plan modeprompt “não edite”modo plan
Subagentes.claude/agents/*.mdsessões separadasagents.json
Comandos.claude/commands/*.mdprompts salvoscomandos próprios

Consequência estratégica

Se os seus ativos (specs, templates, skills) vivem em arquivos neutros — Markdown, YAML, scripts — eles funcionam em qualquer harness. Se vivem “no chat” ou num formato proprietário, você fica preso. O modelo e o harness podem mudar; a spec, o pacote de contexto e os gates devem permanecer.

2.3 — Arquivos que o harness lê sozinho (memória persistente)

Harnesses carregam automaticamente arquivos de regras no início da sessão. É aqui que mora o contexto permanente: 

# AGENTS.md / CLAUDE.md mínimo que funciona

## O que é este projeto
Uma linha de propósito + onde está cada coisa.

## Regras inegociáveis
- Não editar arquivos gerados (liste quais)
- Teste antes de declarar pronto; cole a saída
- Uma entrega por pedido

## Comandos de validação
make test        # suíte principal
npm run lint     # estilo
npm run build    # smoke
Aprendizado do repo

“Contexto persistente deve morar em arquivos de regras/specs; o chat é volátil.” Reenviar o mesmo contexto a cada conversa é o anti-padrão mais caro desta lista — e o mais comum.

2.4 — Permissões: o harness decide o que o modelo pode tocar

Toda ação com efeito colateral (escrever arquivo, rodar comando) passa pela política do harness: aprovar uma a uma, allowlist, ou modo autônomo. A regra segura: autonomia só dentro de escopo versionado — um diretório, um branch, uma fatia. Agente sem cerca é só um processo com sorte.

✏️ Exercício — descubra o seu harness

Responda para o harness que você usa: (1) qual arquivo ele lê no início da sessão? (2) onde ficam as permissões de comando? (3) como alternar entre modo plano e modo edição? (4) onde ele guarda memória entre sessões? Quem não responde as quatro em 10 minutos ainda está dirigindo de olhos vendados.

Módulo 03

Prompt Engineering: instruções que eliminam retrabalho

Prompt engineering não é encontrar palavras mágicas — é fechar decisões antes de o modelo decidir por você. A técnica central deste curso cabe em cinco campos e ~5 linhas.

3.1 — O protocolo de pedido em 5 campos

CONTEXTO:    onde mexer — caminhos de arquivo, não descrições
OBJETIVO:    um resultado observável (um só)
RESTRIÇÕES:  o que não pode mudar; limites (sem lib nova, não tocar em X)
ACEITE:      o comando que prova que ficou pronto
NÃO-META:    o que fica de fora desta entrega
Por que funciona

Cada campo omitido vira uma decisão que o modelo toma pelo caminho estatisticamente comum, não pelo seu. O ACEITE é o campo mais importante: ele transforma “pronto” de opinião em fato verificável (F3 e F6 aplicados à conversa).

3.2 — Exemplo completo: o pedido ruim e o pedido bom

Pedido-romance (anti-padrão real)

“Então, a gente tem aquele sistema de tarefas e eu queria que tivesse um jeito de exportar, porque o pessoal precisa levar pra planilha, e talvez dê pra fazer um botão também, e aproveita e dá uma olhada por que o login tá lento…”

Resultado típico: escopo imprevisível, duas entregas medíocres, zero critério de pronto.

Mesma intenção em 5 campos 
CONTEXTO: docs/curso/.../export_tasks.py;
  tarefas vêm como lista de dicts
OBJETIVO: função que devolve CSV das tarefas
  concluídas do usuário autenticado
RESTRIÇÕES: stdlib apenas; sem I/O;
  ordenar por completed_at desc
ACEITE: pytest -q passa cobrindo autorização,
  ordenação e escaping CSV
NÃO-META: endpoint HTTP e persistência

3.3 — As 7 regras de conduta

  1. Uma entrega por pedido. “Implementa X e aproveita e refatora Y” = duas entregas medíocres. Encadeie pedidos, não escopos.
  2. Peça a prova junto. Termine com “mostre o comando que verifica”. Sem saída de comando, “testes passando” não aconteceu.
  3. Decisão grande → opções antes de código. “Me dê 2–3 opções com trade-offs, não implemente ainda.” Código é a forma mais cara de explorar uma decisão.
  4. Corrija com diff, não com “refaz”. “O campo X deveria vir de Y” converge em 1 iteração; “não gostei” converge nunca.
  5. Referencie por caminho. learner/learning_state.yaml, não “o arquivo de estado”. Ambiguidade de referência é a fonte nº 1 de retrabalho.
  6. Desconfie de afirmação sem artefato. A regra de ouro do ecossistema vale para a conversa.
  7. Prompt repetido vira arquivo. Se você digita a mesma instrução três vezes, ela vira regra (AGENTS.md), template ou skill (Módulo 8).

3.4 — Anti-padrões catalogados (com correção)

Anti-padrãoSintomaCorreção
Pedido-romance20 linhas de história, 0 critério de aceiteCortar para os 5 campos
Escopo-polvo“e também… e já que está aí…”1 objetivo por pedido
Aceite implícito“melhora a performance”“p95 < X ms medido por Y”
Confiança emprestadaAceitar “pronto ✓” sem rodar nadaExigir comando de prova
Contexto reenviadoColar o mesmo bloco em todo chatMover para AGENTS.md

Pegue o último pedido que você fez a uma IA e reescreva-o nos 5 campos. Conte quantas decisões estavam implícitas no original (caminhos, limites, critério de pronto). Cada uma delas era uma decisão que o modelo ia tomar por você.

Módulo 04

Context Engineering: selecionar é medir qualidade

O erro mais caro com IA não é o prompt ruim — é o contexto errado: gigante demais (dilui atenção), incompleto (força invenção) ou com peças contraditórias. Context engineering é montar, para cada tarefa, o menor conjunto de arquivos e regras que torna a tarefa inequívoca.

4.1 — As três classes de contexto

1

Permanente

Regras que valem sempre: AGENTS.md, CLAUDE.md, memória do harness. Vive em arquivo, nunca no chat.

2

Da tarefa

PRD, spec, os arquivos diretamente relacionados, testes e contratos existentes, o recorte de log/erro que explica o problema.

3

Gerado

Saída de ferramentas: diffs, resultados de teste, listagens. Entra no contexto automaticamente a cada ciclo — por isso loops longos precisam de poda.

4.2 — Checklist do pacote de contexto

Incluir

① regras permanentes · ② PRD e spec · ③ arquivos diretamente relacionados (por caminho) · ④ testes e contratos existentes · ⑤ logs/erros recortados que explicam o problema

Excluir

Build output, node_modules/dependências, logs sem recorte, segredos, arquivos sem relação com a tarefa, e views geradas (elas podem estar erradas mesmo com o código certo — inclua a fonte).

4.3 — O pacote real do nosso caso de uso

O workflow testado no final deste curso usou exatamente essa disciplina. O arquivo CONTEXTO.md declara o que entrou e o que ficou de fora:

EntrouFicou de fora
PRD.md e SPEC.md da featureengines/, learner/, curriculum/ (sem relação)
docs/FUNDAMENTOS.md (regras de robustez)node_modules, lockfiles, builds
Um exemplo de “núcleo puro” do curso anteriorHistórico completo do git (349 commits → 20 bastaram)
git log recortado (20 commits).venv e caches (ambiente ≠ contrato)

4.4 — Armadilhas já pagas (do journal do repo)

  • Contexto grande não é contexto bom — selecionar arquivos, regras, testes e erros diretamente relacionados; o resto é ruído que compete por atenção.
  • Artefato derivado pode mentir — uma view gerada estava errada com o código-fonte certo; regenere do run vivo e confira por hash quando importar.
  • Faltou um arquivo no contexto? Registre no AGENTS.md na hora. É assim que o pacote melhora sozinho (Módulo 9).
  • Config copiada de template vence config improvisada — proximidade com um contexto conhecido é mais confiável que invenção.
✏️ Exercício — escreva um CONTEXTO.md de verdade

Para a sua próxima tarefa, escreva CONTEXTO.md antes de abrir o chat: duas tabelas (incluído / excluído, cada linha com o porquê). Se você não consegue justificar por que um arquivo entra, ele não entra. Esse arquivo vira parte da entrega.

Módulo 05

PRD e Specs: da ideia vaga ao requisito executável

Uma ideia vaga entregue a um modelo volta como código confiante e errado. A ponte entre os dois é documentação curta e versionada: o PRD responde por quê, a spec responde como se comporta. Juntas, elas tiram decisões do chat (volátil) e as colocam no repo (auditável).

5.1 — PRD mínimo (responde “por quê?”)

# PRD — <feature>

## Problema        → dor observável, não opinião
## Usuário         → quem se beneficia
## Objetivo        → resultado observável
## Escopo          → comportamentos, um por linha
## Fora de escopo  → o que NÃO será resolvido agora
## Critérios de aceite → checkboxes verificáveis
## Riscos e decisões abertas
O campo mais subestimado

Fora de escopo. Sem ele, toda conversa adiciona “e também…”. Foi exatamente isso que o diagnóstico do repo registrou: pedidos com múltiplos “e também” produzem entregas medíocres e 92 mil linhas de doc para 2 unidades verificadas.

5.2 — Spec técnica (responde “como se comporta?”)

A spec fecha as decisões antes do build:

  • Interface: entradas, saídas, erros — assinatura exata, tipos, formatos;
  • Casos de borda numerados (cada um vira um teste depois);
  • Arquivos permitidos — o agente não pode “aproveitar e mexer” em outros;
  • Estratégia de teste e ordem de implementação;
  • Não-metas — o que o código deliberadamente não faz.
Teste da spec fechada

Se a spec ainda deixa o agente escolher uma decisão importante, ela não está pronta. Registre a decisão como aberta ou resolva-a antes do Build Mode. Não esconda decisões dentro do código — é lá que elas ficam invisíveis para revisão.

5.3 — A transformação, com o caso real deste curso

Do PRD real do caso de uso (release notes):

## Critérios de aceite (do PRD.md real)
- [ ] pytest passa cobrindo: agrupamento, breaking change por `!`
      e por footer, commit fora do padrão, lista vazia, versão no título
- [ ] CLI roda offline com JSON de exemplo e imprime Markdown válido
- [ ] Nenhum commit é descartado silenciosamente: soma das seções
      == número de commits de entrada
- [ ] Saída determinística: mesma entrada, mesma saída

E a spec fechando a interface (trecho do SPEC.md real):

parse_subject(message) -> ParsedCommit | None
generate_release_notes(commits, version=None) -> str  # Markdown

Erros (falha fechada):
- lista vazia            → ValueError("no commits to release")
- commit sem hash/message → ValueError citando o índice
- subject fora do padrão  → seção "Fora do padrão", nunca descarte

Cada critério de aceite virou um teste; cada regra de erro virou um pytest.raises. Critério de aceite é um teste em linguagem humana. Se você não consegue imaginar o teste, o critério ainda está vago.

5.4 — Quando vale a pena escrever?

  • Feature com mais de um arquivo ou mais de uma sessão de trabalho: sempre.
  • Bug com causa conhecida: spec de 5 linhas basta (estado atual → desejado → teste).
  • Experimento descartável: pule a spec, mas escreva o critério de “o que me faria parar”.
✏️ Exercício — especifique antes de pedir

Escolha uma feature pequena do seu projeto. Escreva PRD + spec (30 minutos, máximo). Depois peça a implementação anexando os dois arquivos. Meça quantas perguntas o modelo deixou de fazer e quantas decisões deixaram de ser “surpresa” na revisão do diff. Esse delta é o valor da spec.

Módulo 06

Execução guiada: Plan Mode, Build Mode e validações

Planejar, implementar e validar são papéis diferentes. Quando os três acontecem misturados na mesma corrida, o plano vira improviso e o texto “parece certo” vira conclusão. A execução guiada separa os papéis em fases com portões humanos entre elas.

6.1 — As três fases e seus portões

Plan Mode→ 🧑 humano aprova o plano→ Build Mode (em fatias)→ 🧑 humano confere a validação→ próxima fatia

🗺️ Plan Mode — sem edição

Você está em Plan Mode. Não altere arquivos.
Leia somente o pacote de contexto fornecido.
Entregue: diagnóstico do estado atual,
arquivos afetados, etapas pequenas, riscos,
decisões abertas, testes e critérios de aceite.
Se algo não estiver especificado, pergunte ou
marque como decisão aberta.

O plano só está aprovado quando: respeita o escopo, não inventa contratos, e cada etapa tem uma validação associada. Etapa sem validação é etapa que ninguém consegue conferir.

🔨 Build Mode — uma fatia por vez

Você está em Build Mode.
Implemente somente a etapa <N> do plano
aprovado. Não altere arquivos fora do escopo.
Adicione ou atualize os testes necessários.
Ao final, liste arquivos, decisões, testes
executados e pendências.

Uma fatia deve ser pequena o bastante para que o diff e a falha sejam compreensíveis. Se a fatia estourou, ela vira duas — sem drama, o plano é editável.

6.2 — Validação em camadas (a ordem importa)

Depois de cada fatia, valide de dentro para fora:

teste da fatia→ lint / typecheck→ suíte completa→ build / smoke→ aceite no comportamento real
A frase proibida

“Parece funcionar.” Ela nunca substitui a saída de um comando ou uma observação reproduzível. E cuidado com a camada final: o repo aprendeu do jeito caro que 208 testes podem passar com o produto morto — o caminho que o usuário vê (o iframe, a rota, o CLI) precisa ser exercitado de verdade, não mockado.

6.3 — Teste primeiro quando a spec existe

Com a spec do Módulo 5 fechada, o fluxo natural é: escrever os testes dos casos de borda antes da implementação (RED), implementar até o verde (GREEN), simplificar. Foi exatamente assim que o caso de uso deste curso foi construído:

FaseComandoResultado real
REDpytest test_release_notes.py -qcollection error — módulo não existia
GREEN (1ª implementação)pytest -q1 falhou, 21 passaram — caso de borda real pego
Correçãopytest -q22 passed
Prova finalCLI + diff de duas execuçõessaída idêntica → determinismo provado

A única falha do ciclo foi instrutiva: feat: com descrição vazia caía na seção “fora do padrão” em vez de erro — o parser usava None para duas coisas diferentes. Sem o teste escrito antes, esse bug teria passado silencioso.

✏️ Exercício — force os portões

Na próxima feature, proíba explicitamente a edição no primeiro pedido (“Plan Mode: não altere arquivos”) e aprove o plano por escrito antes do build. Depois implemente em fatias de no máximo ~100 linhas de diff. Conte quantas vezes você precisou dizer “não era isso” — e compare com o seu histórico.

Módulo 07

Agentes e subagentes: delegue sem perder o controle

Um agente é um modelo com ferramentas, um objetivo e (idealmente) uma cerca. Um subagente é uma sessão isolada que recebe uma tarefa fechada e devolve um resultado. Delegação escala o seu trabalho — mas só depois que o fluxo manual está claro e repetível.

Aprendizado do repo (o mais caro do ciclo)

“Agentes especializados só valem a complexidade depois que o fluxo manual está claro e repetível.” O ciclo 1 construiu 14 agentes + 25 subagentes antes de fechar um loop — e ~80% dos commits foram no aparelho, não no currículo. Primeiro o workflow; depois os agentes que o executam.

7.1 — Papéis com contrato (extraídos do workflow permanente)

🔍 Investigadorler e localizarmapa de contexto e riscos

Comece com dois papéis apenas: um implementador e um verificador. A tabela inteira só faz sentido quando o volume exige — e cada papel novo é custo de coordenação permanente.

7.2 — Produtor ≠ verificador (a regra inegociável)

O verificador deve começar do contrato e dos artefatos, nunca da explicação do produtor. No repo, um verificador de contexto fresco reprovou com 4/10 uma entrega que o produtor tinha auto-avaliado em 9/10 sob regra frouxa. O prompt mínimo do verificador: 

OBJETIVO: verificar se <artefato> cumpre o contrato em <spec>.
DONE-RULES: <critérios executáveis, um por linha>.
ARTEFATO: <caminho>.
Não receba o raciocínio de quem produziu. Tente refutar.

7.3 — Regras de operação com múltiplos agentes

  • Paralelismo exige isolamento: diretórios separados paralelizam; arquivos compartilhados serializam. N agentes no mesmo arquivo = corrida.
  • Trabalho não commitado não sobrevive: uma sessão paralela apagou o fonte de 6 jogos porque o resultado dos agentes não foi commitado no mesmo turno.
  • Configs se copiam, não se improvisam: template de projeto (package.json/tsconfig/vite) com nome + porta = verde de primeira; improviso = retry.
  • Prova de identidade é hash, não visão: um agente confundiu o screenshot do jogo 06 com o 07. Quando identidade importa, confira por conteúdo/hash.
  • Falha visível sempre: cada agente reporta fase, bloqueio, artefato pendente e próxima ação — não só “terminei”.

7.4 — Anatomia de um subagente em arquivo

# .claude/agents/revisor-diff.md (funciona em qualquer harness)

## Papel
Revisor de diffs. Somente leitura. Nunca edita.

## Entrada
- caminho do diff ou PR
- spec/contrato que a mudança deve cumprir

## Método
1. Leia a spec primeiro; o diff depois.
2. Tente refutar: escopo violado? teste faltando?
   caso de borda da spec sem cobertura?
3. Não receba a narrativa do implementador.

## Saída
Findings priorizados: bloqueante / importante / nota.
Cada finding cita arquivo + linha + regra violada.
✏️ Exercício — o seu primeiro par produtor/verificador

Pegue uma feature já implementada. Em uma sessão nova (contexto fresco), rode o prompt de verificador acima contra a spec dela. Anote quantos findings aparecem que a sessão produtora nunca mencionou. Se forem zero, ou a spec está perfeita ou o verificador está fraco — os dois casos merecem investigação.

Módulo 08

MCP, ACP e Skills: conecte ferramentas, dados e comportamentos

Três formas de estender o harness, cada uma resolvendo um problema diferente. Primeiro, as siglas — depois, quando usar cada uma.

8.1 — Primeiro, expanda a sigla

🔌 MCP

Model Context Protocol — protocolo aberto para conectar o harness a ferramentas e dados externos: banco de dados, APIs, navegador, arquivos remotos. Padrão servidor ↔ cliente: um servidor MCP expõe tools, resources e prompts; o harness conecta e usa.

🤝 ACP

Agent Client Protocol — protocolo para conectar editores/clientes a agentes: sessões, streaming de saída, aprovações. É o “LSP dos agentes”: desacopla a interface (editor/app) do motor (agente).

🧠 Skills

Comportamento reutilizável em arquivo: um procedimento (Markdown + scripts opcionais) que o agente carrega quando a situação casa. Sem servidor, sem rede — é conhecimento versionado.

8.2 — Ferramentas e dados (MCP na prática)

Um servidor MCP entra quando a tarefa precisa de algo que arquivos locais não resolvem: consultar um banco, abrir um navegador real, chamar uma API interna. A configuração vive em um JSON no projeto: 

// .mcp.json (exemplo ilustrativo)
{
  "mcpServers": {
    "banco-prod": {
      "command": "npx",
      "args": ["-y", "@example/postgres-mcp",
               "--read-only", "--schema=public"]
    }
  }
}
Segurança primeiro

Servidor MCP é código com acesso a dados: instale de fonte confiável, prefira modo somente leitura, restrinja escopo e revise quais tools o agente pode chamar. Um MCP com permissão de escrita num banco de produção é um agente com a chave do cofre.

8.3 — Comportamento reutilizável (Skills na prática)

Toda vez que um procedimento se repete, ele vira skill — Markdown com gatilho, passos e armadilhas, opcionalmente com scripts. A skill mínima: 

# Skill — gerar-release-notes

**Quando usar:** transformar lote de commits em notas
de release sem descartar nada silenciosamente.

## Procedimento
1. Exporte commits para JSON (lista de {hash, message})
2. Rode: python3 release_notes.py commits.json --version vX.Y.Z
3. Revise a seção "Fora do padrão" antes de publicar
4. Quebre a build se o JSON for inválido — nunca release vazio

## Armadilha já paga
`feat: ` (descrição vazia) NÃO é "fora do padrão" —
é erro de entrada. Valide cada classe separadamente.
Esta skill existe de verdade Foi promovida pelo caso de uso deste curso e está em docs/curso-simples/workflow-exemplo/skills/gerar-release-notes.md. Ela codifica uma falha real que aconteceu durante o build — é assim que conhecimento deixa de ser conversa e vira ativo.

Módulo 09

Loop Engineering: implementação, teste e melhoria contínua

Um workflow não é um fluxo que termina — é um ciclo que acumula. Loop engineering é desenhar o ciclo para que cada volta deixe um ativo: a próxima feature começa melhor que a anterior.

9.1 — O loop de uma feature

Especificar→ Planejar→ Implementar (fatias)→ Provar→ Promover↩

📐 Especificar

PRD + spec + pacote de contexto (Módulos 4 e 5). A qualidade do loop é decidida aqui: spec vaga = loop inteiro desperdiçado em retrabalho.

✅ Provar

Validação em camadas + verificação independente quando o risco exige (Módulos 6 e 7). Saída de comando colada — “parece funcionar” não fecha ciclo.

📈 Promover

O passo que quase ninguém faz: transformar o aprendizado da volta em ativo permanente. É o que separa um loop de uma esteira.

9.2 — As 5 perguntas da promoção

Depois da validação, responda — por escrito, 5 minutos:

  1. O modelo assumiu algo errado? (vira regra ou spec mais fechada)
  2. Faltou algum arquivo ou regra no contexto? (vira CONTEXTO.md melhor)
  3. Qual instrução reduziu retrabalho? (vira prompt versionado)
  4. Qual falha merece um teste? (vira teste, não promessa)
  5. O que deve virar template, regra, skill ou decisão?

9.3 — A tabela de promoção (o coração do loop)

Se repetiu……viraOnde vive
Spec com a mesma formaTemplate de specdocs/templates/
Prompt / instruçãoPrompt versionadoAGENTS.md ou comando slash
Checklist / procedimentoSkill.claude/skills/ (ou equivalente)
Erro recorrenteTeste / regra / pitfallSuíte + pitfalls.md
Decisão estruturalADR curtodocs/design/adr/

9.4 — O padrão a evitar: o loop que se auto-verifica

Anti-padrão documentado no repo

Um ciclo de melhoria automática quase reescreveu o documento de fundamentos do próprio repo — o loop otimizava a si mesmo sem contato com uso real. Regra: o loop melhora artefatos; quem decide se o artefato é bom é um humano ou um verificador externo. Verificação só para dentro converge para verificar-se cada vez melhor — e entregar cada vez menos.

✏️ Exercício — feche um loop de verdade

Ao terminar sua próxima feature, responda as 5 perguntas e promova exatamente um ativo (nem dois, nem zero). Anote a data e o gatilho. Depois de 5 features, releia seus ativos: eles são a prova de que o loop acumula — e o seu diferencial composto.

Passo a passo: as 4 capacidades que este curso instala

A promessa final: ser capaz de criar features com previsibilidade, trabalhar com diferentes modelos, montar agentes especializados e transformar specs, instruções e skills em ativos permanentes. Cada capacidade tem um procedimento — nenhum depende de um modelo específico.

Capacidade 1 — Criar features com previsibilidade

  1. Escolha uma fatia pequena. Um comportamento observável, poucos arquivos, risco reversível, um usuário claro, pelo menos um teste automatizável. Se não cabe numa sessão, corte de novo.
  2. Escreva PRD + spec + CONTEXTO.md (Módulos 4 e 5). Trinta minutos. É aqui que a previsibilidade nasce.
  3. Plan Mode → aprovação por escrito → Build Mode em fatias (Módulo 6), cada fatia com o seu comando de validação.
  4. Valide em camadas e cole a saída. A feature só existe quando o comando rodou.
  5. Feche com as 5 perguntas e promova um ativo (Módulo 9).
Por que é previsível Cada etapa tem portão humano e critério verificável. A surpresa não desaparece — ela aparece no Plan Mode (barata) em vez da revisão do diff (cara).

Capacidade 2 — Trabalhar com diferentes modelos

  1. Mantenha os invariantes fora do modelo: mesma spec, mesmo pacote de contexto, mesmo formato de plano, mesmos comandos de validação, mesmo critério de aceite.
  2. Escolha o modelo por tarefa, não por lealdade: raciocínio profundo para arquitetura e trade-offs; modelo rápido para tarefas mecânicas, testes simples e documentação; modelo com ferramentas para exploração e edição incremental.
  3. Teste a troca: rode a mesma spec em dois modelos diferentes e compare os diffs contra os mesmos critérios. Se “pronto” muda com o modelo, o seu processo ainda mora no chat.

Capacidade 3 — Montar agentes especializados

  1. Primeiro o manual: só extraia um agente depois que você já fez o papel à mão pelo menos duas vezes (Módulo 7).
  2. Defina o papel por escrito: pode fazer / deve entregar / nunca faz. Comece pelo par implementador + verificador.
  3. Isole o contexto do verificador: ele recebe contrato + artefato, nunca a narrativa do produtor.
  4. Opere com regras de segurança: diretórios isolados para paralelismo, commit no mesmo turno, falha visível sempre.
  5. Expanda só com demanda: cada papel novo é custo permanente de coordenação.

Capacidade 4 — Transformar tudo em ativos permanentes

  1. Reconheça a repetição: spec repetida, prompt repetido, checklist repetido, erro recorrente — cada um é um ativo pedindo forma.
  2. Promova na hora: a promoção acontece no fim do loop, não “um dia”. Cinco minutos, um arquivo, git commit.
  3. Organize por tipo: templates (docs/templates/), skills (.claude/skills/), ADRs (docs/design/adr/), regras (AGENTS.md).
  4. Use o ativo na próxima feature: ativo que não é usado é doc — e doc não muda comportamento. O teste do ativo é: a próxima feature começou melhor?

Workflow permanente: notas de release a partir de commits

Tudo acima foi aplicado de verdade em um caso de uso do dia a dia de um programador: transformar o histórico de commits em notas de release, agrupando por tipo, destacando breaking changes e sem descartar commits fora do padrão. Esta seção é o walkthrough — com os resultados reais da execução.

22 testes passando commits reais do repo 1 falha real pega e corrigida skill promovida Python stdlib · offline

A tese aplicada

ideia→ PRD→ spec→ contexto→ plano→ build em fatias→ validação→ skill

Uma conversa produz uma resposta. Um workflow produz ativos que melhoram a próxima conversa. Os artefatos estão em docs/curso-simples/workflow-exemplo/ — cada link abaixo é um arquivo real do repo.

Etapa 1 — PRD: o porquê fechado

Trecho real do PRD.md:

## Problema
Montar notas de release manualmente é lento e inconsistente:
cada pessoa agrupa mudanças de um jeito, esquece breaking changes
e perde commits.

## Critérios de aceite
- [ ] pytest passa cobrindo agrupamento, breaking por `!` e por
      footer, fora do padrão, lista vazia, versão no título
- [ ] Nenhum commit é descartado silenciosamente
- [ ] Saída determinística

Etapa 2 — Spec: a interface fechada

# SPEC.md (trecho real)
parse_subject(message) -> ParsedCommit | None
generate_release_notes(commits, version=None) -> str

Ordem fixa de seções (vazias são omitidas):
  Breaking changes → Novidades → Correções →
  Outras mudanças → Fora do padrão

Falha fechada: lista vazia, hash/message ausentes
e descrição vazia → ValueError citando o índice.

Etapa 4 — Build em fatias (GREEN… quase)

A falha real — e o que ela ensinou

feat: com descrição vazia caía na seção “Fora do padrão” em vez de erro. O parser usava None para duas coisas diferentes: “fora do padrão” e “mal formado”. Correção: distinguir as classes (validador genérico perde semântica — aprendizado do journal aplicado ao vivo).

O que levar daqui

Este caso é pequeno de propósito — e completo de verdade. A mesma sequência (PRD → spec → contexto → plano → build → validação → skill) escala para qualquer feature: o tamanho muda, o workflow não. É isso que “previsibilidade” significa: não é a IA acertando sempre, é o processo tornando o erro visível, barato e convertido em ativo.
