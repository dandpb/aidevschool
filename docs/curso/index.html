Fundação

Fundamentos de LLMs

Como modelos processam instruções, contexto, tokens e ferramentas.

Um LLM recebe uma sequência de texto e produz uma continuação provável. Ele não abre o seu repositório inteiro sozinho, não conhece automaticamente o estado atual do sistema e não confirma que a própria resposta está correta. A qualidade depende do que você colocou na mesa de trabalho e de como você verifica o resultado.

InstruçõesDefinem objetivo, prioridade, restrições e formato.
ContextoFatos fornecidos: arquivos, regras, histórico e exemplos.
TokensUnidades de texto processadas. Palavra e token não são sinônimos.
FerramentasConectam o raciocínio ao mundo: ler, editar, executar e testar.

Tokens não são memória infinita

Uma frase pode ser dividida em vários tokens, especialmente com código, pontuação e idiomas diferentes. A contagem exata depende do tokenizer. Contexto demais aumenta custo e pode diluir informações importantes.

Harness

Como Claude Code, Codex e OpenCode organizam modelo, contexto e execução.

Harness é a cabine de operação ao redor do modelo. Ele reúne instruções do projeto, arquivos selecionados, ferramentas, permissões, histórico de sessão e o loop de execução. Claude Code, Codex e OpenCode podem ter interfaces e integrações diferentes, mas a pergunta operacional é a mesma: o que o modelo pode saber, fazer e provar neste passo?

Clareza

Prompt Engineering

Instruções claras reduzem ambiguidade e retrabalho.

Prompt Engineering não é escrever uma redação bonita. É transformar uma intenção em um contrato de comunicação. Um prompt útil responde: qual é o papel, qual resultado é desejado, qual contexto vale, o que não pode mudar, em que formato a resposta deve vir e como saberemos que terminou.

Papel+Objetivo+Contexto+Restrições+Aceite

Seleção

Context Engineering

Selecionar arquivos, regras e memórias relevantes é parte da implementação.

Context Engineering é curadoria de evidência. O modelo só consegue raciocinar sobre o que recebe, mas “receber tudo” aumenta ruído, custo e contradições. O pacote deve ser pequeno o bastante para manter foco e completo o bastante para não esconder o contrato.

01Regras permanentesAGENTS.md, CLAUDE.md, convenções e limites
02Contrato da tarefaPRD, spec, critérios e decisões
03Código executadoarquivos relacionados, interfaces e testes
04Evidência recenteerro recortado, diff, saída do comando
+ Pacote para exportar CSV

- src/tasks/tasks.service.ts

Memória não é transcrição

Uma decisão reutilizável vira regra, spec, pitfall ou skill. Histórico bruto só entra quando ajuda a explicar o estado atual.

Pergunta de seleção

Se eu remover este arquivo, o agente ainda consegue tomar a decisão desta etapa?

Contrato

PRD e Specs

Transforme uma ideia vaga em requisitos que outra pessoa consegue executar e validar.

PRD responde “por quê?”

Problema, usuário, objetivo, escopo, não-metas, critérios de valor e riscos. É o contrato do produto.

# PRD — nome da feature

## Problema
## Usuário
## Objetivo
## Escopo
## Fora de escopo
## Critérios de aceite
## Riscos

Spec responde “como se comporta?”

Estado atual, estado desejado, entradas, saídas, erros, arquivos, testes e ordem de implementação.

# SPEC — nome da feature

## Interface
## Regras e bordas
## Arquivos afetados
## Testes
## Plano
## Não-metas

Transformação: ideia → contrato

IDEIA VAGA

“Quero que o aluno consiga acompanhar o progresso.”

↓
SPEC EXECUTÁVEL

“Na página do curso, exibir uma checklist local com 9 módulos. O aluno marca cada módulo manualmente. O estado não é enviado para servidor. O progresso deve aparecer como ‘X de 9’, funcionar sem JavaScript e manter foco visível.”

Critério de aceite é um teste em linguagem humana

  • O comportamento pode ser observado.
  • O resultado esperado é inequívoco.
  • O caso de erro ou vazio está descrito.
  • O que não será entregue está explícito.

06
Ritmo

Execução guiada

Plan Mode, Build Mode e validações que impedem “pronto” prematuro.

Separe pensar, fazer e verificar. A separação pode ser manual no começo; o ganho vem de não misturar decisões e edição no mesmo salto.

01Plan Mode

Somente leitura. Diagnóstico, arquivos afetados, alternativas, riscos, etapas e testes.

Não altere arquivos.
Leia apenas o pacote de contexto.
Entregue um plano em fatias pequenas.
Marque decisões abertas.
02Build Mode

Execução de uma etapa aprovada. Diff pequeno, testes junto e nenhuma expansão silenciosa de escopo.

Implemente apenas a etapa 1.
Não altere fora do escopo.
Adicione os testes da etapa.
Liste pendências ao final.
03Validate Mode

Comandos e observação. Falhas viram dados para o próximo loop, não motivo para fingir que funcionou.

teste específico
→ lint/typecheck
→ suíte completa
→ build/smoke
→ critérios de aceite
Spec aprovada→Plano revisado→Fatia implementada→Gate de validação→Próxima fatia
Quando rejeitar um plano?

Quando ele inventa arquivos não vistos, mistura tarefas, não prevê testes, altera uma fronteira de segurança ou não tem um critério verificável para terminar.

Comandos típicos

pytest, npm run lint, pnpm test, smoke browser ou o comando canônico do projeto.

Armadilha

Rodar um build enorme antes de entender a tarefa. O erro fica grande demais para diagnosticar.

Exercício · 8 min

Delegação

Agentes e subagentes

Delegue partes bem definidas sem perder o controle do resultado.

Um agente especializado não é apenas “outro chat”. Ele é uma combinação de objetivo, contexto, ferramentas, permissões, formato de saída e gate. Delegue quando a tarefa puder ser delimitada e revisada. Não delegue a responsabilidade final.

Produtor ≠ verificador. A revisão começa pelo contrato e pelos artefatos, não pela narrativa do produtor.

08
Extensões

MCP, ACP e Skills

Conecte capacidades sem transformar toda tarefa em infraestrutura.

MCP

Ferramentas e dados

Uma forma padronizada de expor ao modelo capacidades como repositório, documentação, banco ou execução.

ACP

Comunicação e controle

Neste curso, usamos ACP como a camada de contratos entre agentes: mensagens, identidade, permissões, ack e escalonamento. Confirme a definição específica da sua ferramenta.

SKILL

Comportamento reutilizável

Procedimentos versionados que combinam instruções, checklist e, quando necessário, scripts.

+ Exemplo conceitual de ferramenta
{
  "name": "repo-tests",
  "purpose": "executar somente a suíte da feature",
  "input": { "path": "tests/tasks/" },
  "output": "comando, status e saída",
  "permission": "read + run; sem deploy"
}

O JSON é ilustrativo. O ponto é o contrato: nome, propósito, entrada, saída e limite.

Skill mínima

# Skill: criar feature verificável

1. Ler regras e spec.
2. Montar contexto mínimo.
3. Fazer plano sem editar.
4. Implementar uma fatia.
5. Rodar teste e revisar diff.
6. Registrar limites e aprendizado.

Quando adicionar?

  • O processo já aconteceu mais de uma vez.
  • Os passos são estáveis.
  • Existe um ganho claro de repetição.
  • O limite de ação está explícito.
  • Você consegue testar a skill sem confiar no “parece bom”.
Comece com Markdown

Uma skill simples em arquivo é um ativo permanente. Automatize via MCP ou um agente só depois de provar que o procedimento manual funciona.

Armadilha

Adicionar MCP, ACP ou um roster de agentes antes de saber qual repetição está sendo resolvida.

09
Melhoria contínua

Loop Engineering

Cada feature deve melhorar o sistema de trabalho que produzirá a próxima.

Engenharia com IA não é linear. Há um loop interno de editar → executar → ler o erro → corrigir, um loop externo de spec → build → teste → review e um meta-loop que transforma o aprendizado em memória, regra, template ou skill.

LOOP EXTERNO
spec → build → review
LOOP INTERNO
editar → testar → corrigir
META-LOOP
aprender → reutilizar
01

Especificar

Reduzir incerteza antes de pagar o custo da implementação.

02

Provar

Executar a validação real e registrar a falha sem esconder o ruído.

03

Promover

Transformar padrão repetido em ativo permanente do workflow.

Spec repetida→template de spec
Prompt que funcionou→prompt versionado
Erro recorrente→teste ou regra
Checklist repetido→skill

Depois da aula

Transforme o aprendizado em capacidade permanente

Este é o roteiro para usar em qualquer feature, com qualquer modelo e em qualquer harness.

01

Features com previsibilidade

  1. Escolha uma fatia pequena e reversível.
  2. Escreva PRD, spec e critérios.
  3. Selecione contexto mínimo.
  4. Rode Plan Mode e revise o plano.
  5. Implemente em fatias.
  6. Valide com comandos e observação real.
02

Trabalhar com diferentes modelos

  1. Mantenha a spec e o gate fora do modelo.
  2. Use modelo forte para decisões e review.
  3. Use modelo rápido para tarefas mecânicas.
  4. Compare saídas com o mesmo contexto.
  5. Escolha por tarefa, não por lealdade.
03

Montar agentes especializados

  1. Extraia uma repetição que já funciona.
  2. Defina entrada, permissão e saída.
  3. Dê ao agente somente o contexto necessário.
  4. Crie um gate de revisão.
  5. Escalone para humano em decisões consequentes.
04

Criar ativos permanentes

  1. Prompt que se repete vira template.
  2. Checklist vira skill.
  3. Decisão vira ADR.
  4. Erro recorrente vira teste ou regra.
  5. Spec e evidência ficam versionadas no repositório.
