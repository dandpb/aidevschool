Fundação

Fundamentos de LLMs

Como modelos processam instruções, contexto, tokens e ferramentas.

Um LLM recebe uma sequência de texto e produz uma continuação provável. Ele não abre o seu repositório inteiro sozinho, não conhece automaticamente o estado atual do sistema e não confirma que a própria resposta está correta. A qualidade depende do que você colocou na mesa de trabalho e de como você verifica o resultado.

InstruçõesDefinem objetivo, prioridade, restrições e formato.
ContextoFatos fornecidos: arquivos, regras, histórico e exemplos.
TokensUnidades de texto processadas. Palavra e token não são sinônimos.
FerramentasConectam o raciocínio ao mundo: ler, editar, executar e testar.

Tokens não são memória infinita

Uma frase pode ser dividida em vários tokens, especialmente com código, pontuação e idiomas diferentes. A contagem exata depende do tokenizer. Contexto demais aumenta custo e pode diluir informações importantes.

O ambiente

Harness

Como Claude Code, Codex e OpenCode organizam modelo, contexto e execução.

Harness é a cabine de operação ao redor do modelo. Ele reúne instruções do projeto, arquivos selecionados, ferramentas, permissões, histórico de sessão e o loop de execução. Claude Code, Codex e OpenCode podem ter interfaces e integrações diferentes, mas a pergunta operacional é a mesma: o que o modelo pode saber, fazer e provar neste passo?

Os nomes não são o contrato

Plan, Build, permissões e subagentes variam por versão e instalação. Preserve PRD, spec, contexto permitido e gates fora do harness para trocar de ferramenta sem redefinir “pronto”.

→ Configuração mental de um harness
ALLOWED_CONTEXT = [PRD.md, SPEC.md, src/tasks/, tests/tasks/]
ALLOWED_ACTIONS = [read, edit(scope=src/tasks), run(test)]
FORBIDDEN = [secrets, node_modules, deploy]
GATE = "o teste e os critérios de aceite precisam passar"
Analogia

Modelo é o piloto. Harness é a cabine, o mapa, os instrumentos e os limites de segurança.

Clareza

Prompt Engineering

Instruções claras reduzem ambiguidade e retrabalho.

Prompt Engineering não é escrever uma redação bonita. É transformar uma intenção em um contrato de comunicação. Um prompt útil responde: qual é o papel, qual resultado é desejado, qual contexto vale, o que não pode mudar, em que formato a resposta deve vir e como saberemos que terminou.

Seleção

Context Engineering

Selecionar arquivos, regras e memórias relevantes é parte da implementação.

Context Engineering é curadoria de evidência. O modelo só consegue raciocinar sobre o que recebe, mas “receber tudo” aumenta ruído, custo e contradições. O pacote deve ser pequeno o bastante para manter foco e completo o bastante para não esconder o contrato.

PRD responde “por quê?”

Problema, usuário, objetivo, escopo, não-metas, critérios de valor e riscos. É o contrato do produto.

Estado atual, estado desejado, entradas, saídas, erros, arquivos, testes e ordem de implementação.

  • O resultado esperado é inequívoco.

06
Ritmo

Execução guiada

Plan Mode, Build Mode e validações que impedem “pronto” prematuro.

Separe pensar, fazer e verificar. A separação pode ser manual no começo; o ganho vem de não misturar decisões e edição no mesmo salto.

01Plan Mode

Somente leitura. Diagnóstico, arquivos afetados, alternativas, riscos, etapas e testes.

Não altere arquivos.
Leia apenas o pacote de contexto.
Entregue um plano em fatias pequenas.
Marque decisões abertas.
02Build Mode

Execução de uma etapa aprovada. Diff pequeno, testes junto e nenhuma expansão silenciosa de escopo.

Implemente apenas a etapa 1.
Não altere fora do escopo.
Adicione os testes da etapa.
Liste pendências ao final.
03Validate Mode

Comandos e observação. Falhas viram dados para o próximo loop, não motivo para fingir que funcionou.

teste específico
→ lint/typecheck
→ suíte completa
→ build/smoke
→ critérios de aceite
Spec aprovada→Plano revisado→Fatia implementada→Gate de validação→Próxima fatia
Quando rejeitar um plano?

Quando ele inventa arquivos não vistos, mistura tarefas, não prevê testes, altera uma fronteira de segurança ou não tem um critério verificável para terminar.

Comandos típicos

pytest, npm run lint, pnpm test, smoke browser ou o comando canônico do projeto.

Armadilha

Rodar um build enorme antes de entender a tarefa. O erro fica grande demais para diagnosticar.

Agentes e subagentes

Delegue partes bem definidas sem perder o controle do resultado.

Um agente especializado não é apenas “outro chat”. Ele é uma combinação de objetivo, contexto, ferramentas, permissões, formato de saída e gate. Delegue quando a tarefa puder ser delimitada e revisada. Não delegue a responsabilidade final.

08
Extensões

MCP, ACP e Skills

Conecte capacidades sem transformar toda tarefa em infraestrutura.

MCP

Ferramentas e dados

O Model Context Protocol conecta host, cliente e servidor via JSON-RPC. Servidores expõem recursos, prompts e ferramentas com contratos e consentimento explícitos.

ACP

Primeiro, expanda a sigla

Agent Client Protocol liga um agente a um cliente como uma IDE. Agent Control Protocol é outro projeto, voltado a operar interfaces. Para agente → agente, cite o protocolo concreto; “ACP” sozinho é ambíguo.

SKILL

Comportamento reutilizável

Procedimentos versionados, normalmente em SKILL.md com instruções e recursos. Cada harness pode acrescentar regras próprias de descoberta e execução.

Não confunda integração com orquestração

MCP conecta capacidades; Agent Client Protocol conecta agente e cliente; uma Skill reutiliza comportamento. Nenhum deles substitui spec, autorização, validação ou o contrato entre produtor e verificador.

+ Exemplo conceitual de ferramenta
{
  "name": "repo-tests",
  "purpose": "executar somente a suíte da feature",
  "input": { "path": "tests/tasks/" },
  "output": "comando, status e saída",
  "permission": "read + run; sem deploy"
}

O JSON é ilustrativo. O ponto é o contrato: nome, propósito, entrada, saída e limite.

Skill mínima

# Skill: criar feature verificável

1. Ler regras e spec.
2. Montar contexto mínimo.
3. Fazer plano sem editar.
4. Implementar uma fatia.
5. Rodar teste e revisar diff.
6. Registrar limites e aprendizado.

Quando adicionar?

  • O processo já aconteceu mais de uma vez.
  • Os passos são estáveis.
  • Existe um ganho claro de repetição.
  • O limite de ação está explícito.
  • Você consegue testar a skill sem confiar no “parece bom”.
Comece com Markdown

Uma skill simples em arquivo é um ativo permanente. Automatize via MCP ou um agente só depois de provar que o procedimento manual funciona.

Loop Engineering

Cada feature deve melhorar o sistema de trabalho que produzirá a próxima.

Engenharia com IA não é linear. Há um loop interno de editar → executar → ler o erro → corrigir, um loop externo de spec → build → teste → review e um meta-loop que transforma o aprendizado em memória, regra, template ou skill.

LOOP EXTERNO
spec → build → review
LOOP INTERNO
editar → testar → corrigir
META-LOOP
aprender → reutilizar

6 conclusões que atravessam os ciclos

01 · Escopo

Selecione antes de serializar

Allowlist, filtros exatos e caminhos canônicos reduzem vazamento e tornam a saída auditável.

02 · Validação

Valide tudo antes de derivar

Uma linha ruim, um ID duplicado ou uma dependência ausente invalida o conjunto antes da persistência.

03 · Tempo

Relógio é entrada, não ambiente

Retry e TTL ficam reproduzíveis quando now e o início da agenda entram na fixture.

04 · Ordem

Elegibilidade vem antes do ranking

Primeiro remova o que não pode participar; depois ordene, priorize ou aplique capacidade.

05 · Forma

Uma saída canônica elimina bifurcações

Versões, caminhos e ordens estáveis permitem comparar modelos e execuções pelos mesmos bytes.

06 · Segurança

Falhe fechado e redija antes de reportar

Políticas estreitas negam o desconhecido; relatórios nunca repetem o segredo que encontraram.

  1. ciclo 01logs

    Filtrar NDJSON sem esconder entrada inválida

    Isola os erros de uma requisição em logs estruturados, usando filtros exatos combinados por AND.

    Por que importa
    Você investiga um incidente sem aceitar um log parcialmente corrompido como verdade.
    Exemplo
    Quatro linhas; filtro req-7 + error.
    Resultado observado
    2 registros e counts_by_level.error = 2.
    Gate
    Uma linha malformada encerra o ciclo com o número da linha e sem escrita parcial.
    Acumula
    ndjson-exact-and-filter, reutilizado nos ciclos 05 e 08.
    Ver entrada →Ver resultado JSON →
  2. ciclo 02configuração

    Aplicar patch JSON com troca atômica

    Atualiza somente chaves de primeiro nível; objetos aninhados são substituídos por inteiro e null continua sendo um valor.

    Por que importa
    Evita configurações meio aplicadas e merges profundos que o contrato nunca prometeu.
    Exemplo
    enabled vira falso; limits é substituído; note recebe null.
    Resultado observado
    region permanece, burst = 8 e steady sai da forma final.
    Gate
    Documento e patch precisam ser objetos completos antes de produzir saída.
    Acumula
    validate-before-atomic-replace, consumido pela migração do ciclo 09.
    Ver entrada →Ver resultado JSON →
  3. ciclo 03confiabilidade

    Calcular retries sem dormir nem ler o relógio

    Transforma horário inicial, tentativas, base e teto em uma agenda de backoff exponencial reproduzível.

    Por que importa
    Backoff vira lógica testável, sem sleep, flake ou relógio escondido.
    Exemplo
    5 tentativas, base 3 s, teto 10 s, início às 12:00:00Z.
    Resultado observado
    Atrasos 0, 3, 6, 10, 10; última tentativa às 12:00:29Z.
    Gate
    Tempo UTC canônico e inteiros positivos; duas execuções geram os mesmos bytes.
    Acumula
    time-is-explicit-input, aplicado ao cache do ciclo 04.
    Ver entrada →Ver resultado JSON →
  4. ciclo 04cache

    Expirar TTL antes de decidir a evasão LRU

    Produz um snapshot auditável: remove expirados na fronteira expires_at ≤ now e só depois aplica capacidade.

    Por que importa
    Impede expulsar uma entrada viva enquanto uma chave já expirada ainda ocupa capacidade.
    Exemplo
    now = 12:00Z, capacidade 2 e alpha expira exatamente na fronteira.
    Resultado observado
    alpha expira, beta é evictada e delta/gamma permanecem.
    Gate
    Tempo injetado, chaves únicas e desempate lexical determinístico.
    Acumula
    eligibility-before-ranking, usado no planejador do ciclo 05.
    Ver entrada →Ver resultado JSON →
  5. ciclo 05planejamento

    Ordenar tarefas e calcular o caminho crítico

    Transforma dependências de implementação em uma ordem executável e mostra a duração da cadeia mais longa.

    Por que importa
    Expõe bloqueios e a sequência mínima antes de vários agentes começarem a editar.
    Exemplo
    fetch → lint → build → test → package, com duração por tarefa.
    Resultado observado
    Ordem topológica igual ao exemplo e caminho crítico de 9 minutos.
    Gate
    ID duplicado, dependência ausente ou ciclo invalidam o plano inteiro.
    Acumula
    Reúne parsing exato e elegibilidade antes de promover validate-complete-plan.
    Ver entrada →Ver resultado JSON →
  6. ciclo 06arquivos

    Planejar renomes em dry-run

    Valida um lote de renomes antes de tocar no filesystem, mantendo fontes e destinos dentro do escopo declarado.

    Por que importa
    Transforma uma mutação em plano revisável e reversível antes de tocar nos arquivos.
    Exemplo
    docs/a.txt e docs/b.txt são destinados a archive/.
    Resultado observado
    dry_run: true, 2 operações ordenadas e nenhuma mutação no filesystem.
    Gate
    Rejeita traversal, barra invertida, fonte ausente e colisão de destino.
    Acumula
    canonical-root-relative-paths, reutilizado no review e no scanner.
    Ver entrada →Ver resultado JSON →
  7. ciclo 07review

    Checar um diff unificado com política estreita

    Conta arquivos e linhas alteradas em patches de texto do mesmo caminho, sem fingir ser um parser universal de Git.

    Por que importa
    Um gate estreito é verificável; um “parser universal” improvisado cria falsa confiança.
    Exemplo
    2 caminhos permitidos, no máximo 2 arquivos e 4 linhas alteradas.
    Resultado observado
    allowed: true, changed_lines: 4 e reasons: [].
    Gate
    Diff malformado falha; caminho ou orçamento fora da política produz negação explícita.
    Acumula
    fail-closed-narrow-policy, exigido pelo scanner do ciclo 10.
    Ver entrada →Ver resultado JSON →
  8. ciclo 08observabilidade

    Resumir access logs com quantis declarados

    Conta métodos e status e calcula p50/p95 pela regra de posto mais próximo, sem serviço externo.

    Por que importa
    Métricas operacionais só ajudam quando todas as linhas obedecem à mesma gramática e regra de quantil.
    Exemplo
    5 requisições GET/POST, status 2xx/4xx/5xx e latências fixas.
    Resultado observado
    GET = 3, POST = 2, p50 = 100 e p95 = 400 ms.
    Gate
    Todas as linhas passam por uma gramática fechada; até linha vazia interrompe a derivação.
    Acumula
    validate-all-before-derive, reutilizado na migração do ciclo 09.
    Ver entrada →Ver resultado JSON →
  9. ciclo 09migração

    Normalizar registros v1 e v2

    Aceita dois contratos exatos, rejeita campos ambíguos e produz somente a forma canônica v2 ordenada por ID.

    Por que importa
    Uma forma canônica impede que todo consumidor carregue ramificações para versões antigas.
    Exemplo
    Grace entra como v1 e Ada como v2.
    Resultado observado
    Ambas saem como v2, ordenadas por u-1 e u-2.
    Gate
    Versão, campos, strings e IDs são validados antes de migrar a coleção.
    Acumula
    canonical-version-output, uma das três dependências finais.
    Ver entrada →Ver resultado JSON →
  10. ciclo 10segurança

    Encontrar segredos sintéticos sem vazá-los no relatório

    Escaneia arquivos explicitamente fornecidos, reporta posição e categoria e redige cada ocorrência na prévia.

    Por que importa
    Um relatório de segurança não pode repetir o segredo que acabou de detectar.
    Exemplo
    3 arquivos; um LABKEY, um LABTOKEN e um arquivo limpo.
    Resultado observado
    2 achados; ambas as prévias contêm [REDACTED] e nenhum valor original.
    Gate
    Escopo canônico, caminhos únicos e padrões sintéticos fixos; nenhum valor reconhecido chega ao artefato.
    Acumula
    Consome três lições anteriores e promove redact-before-reporting.

Ativos operacionais · três responsabilidades

Skill pack permanente

O laboratório deixa de depender de uma conversa específica: construir, verificar e promover passam a ter contratos versionados e deliberadamente separados.

Abrir índice humano →
01 · produtorBuild

workflow-lab-build

Use ao adicionar ou alterar um ciclo. A skill possui fixture, contrato, handler e teste focado em um loop red → green.

Por que importa
Limita o produtor à menor mudança executável e impede que ele aprove a própria entrega.
Gate
Teste focado e suíte do laboratório verdes, diff restrito e grafo de requires válido.
Stop
Não atualiza evidência final, HTML nem emite veredito independente.
Ler a skill canônica →
02 · verificadorVerify

workflow-lab-verify

Use após uma mudança ou antes de publicar resultados. A skill é somente leitura e executa a prova em duas saídas temporárias novas.

Por que importa
Separa evidência de produção e detecta regressão, diferença de bytes ou dependência escondida do diretório atual.
Gate
61 testes, CLI canônico, 12 arquivos idênticos, lições resolvidas, outro cwd e validador do curso.
Stop
Entrega PASS/FAIL com comandos e divergências; nunca corrige código ou evidência.
Ler a skill canônica →
03 · promotorMaintain

workflow-lab-maintain

Use somente depois de um Verify independente em PASS. A skill sincroniza contrato, evidência durável, ensinamentos, índice e manifesto.

Por que importa
Evita que página, relatório e skills contem uma história diferente do runtime realmente verificado.
Gate
Zero divergências entre spec, fixtures, registry, evidência, HTML e documentação; depois, novo Verify independente.
Stop
Defeito de runtime volta para Build; Maintain não reescreve documentação para esconder uma falha.
Ler a skill canônica →
Build produz→Verify prova em outro contexto→Maintain promove→Novo Verify confirma
Como manter funcionando

As skills não rodam sozinhas nem substituem julgamento. Invoque Build em mudanças de runtime, Verify após qualquer mudança e Maintain apenas para promover um estado que já recebeu PASS independente.

Depois da aula

Transforme o aprendizado em capacidade permanente

Este é o roteiro para usar em qualquer feature, com qualquer modelo e em qualquer harness.

01

Features com previsibilidade

  1. Escolha uma fatia pequena e reversível.
  2. Escreva PRD, spec e critérios.
  3. Selecione contexto mínimo.
  4. Rode Plan Mode e revise o plano.
  5. Implemente em fatias.
  6. Valide com comandos e observação real.
02

Trabalhar com diferentes modelos

  1. Mantenha a spec e o gate fora do modelo.
  2. Use modelo forte para decisões e review.
  3. Use modelo rápido para tarefas mecânicas.
  4. Compare saídas com o mesmo contexto.
  5. Escolha por tarefa, não por lealdade.
03

Montar agentes especializados

  1. Extraia uma repetição que já funciona.
  2. Defina entrada, permissão e saída.
  3. Dê ao agente somente o contexto necessário.
  4. Crie um gate de revisão.
  5. Escalone para humano em decisões consequentes.
04

Criar ativos permanentes

  1. Prompt que se repete vira template.
  2. Checklist vira skill.
  3. Decisão vira ADR.
  4. Erro recorrente vira teste ou regra.
  5. Spec e evidência ficam versionadas no repositório.
Ideia→PRD→SPEC→Plano→Testes→Skill→Próxima feature melhor
Comece agora · 30 minutos

Uma primeira sessão que termina em entrega

  1. Escolha uma feature pequena.
  2. Escreva uma spec de uma página.
  3. Selecione 3–6 arquivos relevantes.
  4. Peça um plano sem permitir edição.
  5. Implemente uma fatia com teste.
  6. Rode a validação e registre um aprendizado.

Não construa a plataforma de agentes primeiro. Construa um caminho que um aluno consegue repetir.
